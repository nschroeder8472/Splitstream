# Operational Learnings

Experiential patterns from practice. Complements standards (what should be) with experience (what we keep learning).

## Design Patterns

- 2026-07-18 [design] Interface-at-consumer for OS-API seams — when a crate wraps platform APIs, define port traits in the consumer crate, not the wrapper; otherwise the wrapper's platform deps break cross-platform tests.
- 2026-07-18 [design] Live control of RT systems splits cleanly: param changes via lock-free commands, structural changes via supervisor rebuild — the RT no-alloc/no-block rule decides which side a change falls on.
- 2026-07-18 [design] Keep third-party transport types (ring/channel libs) out of port trait signatures — pass slices, own the transport in the orchestrator; mocks stay trivial and the lib stays swappable.
- 2026-07-18 [design] Model feedback loops as pure `tick(measurements) -> commands` — unit-testable with synthetic curves, no threads or OS in the test.
- 2026-07-18 [design] Start control loops with only the directly-held error signal; add feedforward inputs (extra sensors/APIs) only when evidence shows slow convergence.
- 2026-07-18 [design] Extend an existing port facade with a method instead of adding a new single-consumer trait — a second abstraction needs a second consumer. Amended 2026-07-18: facade growth stops at concern boundaries — must-work and may-fail/feature-gated surfaces get separate traits even with one consumer each. Amended 2026-07-21: when the new capability is backend-specific and most implementors (mocks, other backends) have nothing meaningful to do with it, give the trait method a default no-op body rather than making every implementor add one — `AudioSystem::set_bus_match` (simple-launch.md) reached `WasapiSystem` without any change to `MockSystem` or its test call sites. Stays dyn-safe (no generics in the signature) and keeps the change's blast radius to the one backend that actually needs it.
- 2026-07-18 [design] Manage external mutable state (OS prefs, remote config) as desired-state reconciliation with an applied-map — idempotent, re-runnable on any change, never rewrites what's already applied.
- 2026-07-18 [design] Trace latency through the whole mutation path before committing to single-funnel designs — file-watcher round-trips are 100s of ms; interactive controls need a fast path carrying the same value, source of truth unchanged.
- 2026-07-18 [design] Machine edits to user-editable files: semantic edit enum → format-preserving editor → atomic rename → echo suppression, as one package. Never raw-text patching, never re-serialize.
- 2026-07-18 [design] When a later design level invalidates an earlier decision, revise it explicitly with a logged revision entry — not silently. Keeps the decision log trustworthy.
- 2026-07-18 [design] Structural changes to RT-owned state: pre-build off-thread → pointer-swap via command → return old state for off-thread drop. Glitch-free, alloc-free on the hot path.
- 2026-07-18 [design] Processing that spans entities (sidechains, cross-feeds) doesn't fit per-entity pipeline traits — hoist to the orchestrator instead of widening the trait with params most stages ignore.
- 2026-07-18 [review] After designing multiple features against shared contracts, run a dedicated cross-blueprint seam review — event fan-out, channel producer counts, id stability across rebuilds, thread pacing. Per-feature reviews structurally miss these.
- 2026-07-19 [design] When implementation drops a spec'd domain field (e.g. `Format.layout`), capability silently narrows — the hard-fail surfaces at real-hardware boundaries, not in mocks, because mocks are built with matching formats. Diff implemented value objects against the spec's domain model when a gap appears.
- 2026-07-19 [design] When a feature's purpose is removing a failure class, make its core constructor infallible — fold unknown inputs with normalization rather than reintroducing strict errors at the edges (channel-mixdown: unknown speaker positions fold at −3 dB instead of erroring).
- 2026-07-19 [design] For format/audio conversion design, research the governing standard first (ITU-R BS.775, RFC 7845, FFmpeg's matrix model) — the standard's static-matrix formulation made RT-safety (pre-allocated, pure, infallible) fall out for free.
- 2026-07-20 [design] When a design revision names a component as owning a mutating handle for a stated purpose (e.g. "EventPump calls routing.update_topology on structural events"), verify the underlying event stream can actually deliver the signal that purpose depends on before implementing it literally — here no `EngineEvent` variant signaled "routes changed," so a polling read-only view (`RoutingReader`) was strictly more correct than the event-driven design the revision sketched.
- 2026-07-20 [design] For perceptual-audio features, check whether ecosystem libraries' moving-source generality is actually needed before adopting one — fixed-position virtualization (spatial-audio) collapses to per-channel static convolution, far simpler and RT-safer than general 3D spatializers (`hrtf` crate's sphere interpolation, click artifacts). Studying the commercial reference implementation (HeSuVi/Equalizer APO) is what revealed the collapse; same spirit as the research-the-governing-standard rule.
- 2026-07-20 [design] Adding an alternative processing path to an existing pipeline slot: model it as an enum replacing the existing field (`Render::Matrix | Spatial`) plus a widened retire type on the existing swap-and-retire channel — not a trait (two known variants, one consumer) and not a parallel field (two paths live, one dead). Reuses the swap/epoch/off-RT-drop machinery wholesale; downstream stages untouched.
- 2026-07-20 [design] An elevated machine-wide installer is the wrong actor for per-user state — config in `%APPDATA%` and autostart in the HKCU Run key belong to the *end* user, but the installer runs as admin. Hand config bootstrap + autostart to the app's own first-run (launched `runasoriginaluser`), keeping the installer to binary/shortcut/uninstaller only. Recurring Windows-packaging trap; also keeps a single reconcile path (the app already reconciles `set_autostart` every startup) instead of the installer and app both writing the Run key.
- 2026-07-20 [design] When a blueprint assumes fetchable external data (a measured HRIR set, a downloaded reference dataset, ...) and it turns out unreachable at implementation time (no network access this session), preserve the public API/contract shape and swap the *internal* construction strategy instead of blocking the feature or silently guessing — surface the tradeoff to the user first (spatial-audio's `HrirSet::embedded` ended up procedurally synthesizing ITD/ILD cues instead of decoding measured tables; every downstream contract stayed identical).

- 2026-07-22 [design] When a design pivot swaps the underlying OS primitive for a capability (WASAPI per-app redirect → process-loopback capture), explicitly audit what the OLD primitive gave for free that the NEW one doesn't — not just whether the new one satisfies the capability list as written. A redirect silences the original path inherently (it moved); a tap/capture does not. Nothing in process-loopback-capture's Level 1 named "silence the original" because under the old model it wasn't a feature, it was a side effect of how redirect worked — the gap (session-mute-on-capture) only surfaced from actually listening to real audio, since the capture→mix→render pipeline's own tests have no way to model "is the untouched original also still audible outside the system under test."
- 2026-07-21 [design] When production instability keeps tracing back to the same architectural area, question the spec's own stated *rationale* for that area, not just the implementation built on top of it — a platform-API claim ("no supported per-session PCM capture") can be outdated or simply wrong even when it was accurate at write time, superseded by a later OS release the original author didn't know about. Caught here only because the debugging session kept failing to root-cause instability in an undocumented-API-based design; re-deriving from first principles ("is this claim even still true?") found a documented replacement API that eliminated the whole fragile surface rather than patching around it.
- 2026-07-21 [design] Cloneable `*Control`/`*Reader` handles (`RoutingHandle::reader() -> RoutingReader`, `EngineHandle::capture_control() -> CaptureControl`) are this codebase's established idiom for giving a second thread safe access to RT-adjacent shared state without transferring single-owner resources (a `JoinHandle`, a `Receiver`) that make the owning type itself non-`Clone`. Reach for this by name — a small wrapper struct cloning only the `Arc<Mutex<..>>`/`Arc<..>` fields a caller actually needs — instead of re-deriving the shape from scratch each time a new cross-thread capability is needed.
- 2026-07-21 [design] When a prior decision names a specific missing capability as its reason ("no device-enumeration read model to back a picker"), check whether a later feature actually built that capability before layering new UI on the old workaround — reverse the old decision explicitly (mixer-ui-redesign's dropdown-backed pickers reversing app-shell.md's draft-then-commit text-field decision) rather than leaving both patterns coexisting.
- 2026-07-21 [design] A discrete-selection widget (dropdown/combo) never needs the draft-then-commit pattern free-text fields need — only typing has in-progress state worth protecting. When a text-field-plus-commit-button becomes dropdown-backed, drop the draft state entirely rather than carrying the pattern over out of habit.
- 2026-07-22 [design] Dropping a draft field in favor of reading a dropdown's current value fresh each frame (the pattern above) works fine once the underlying value already exists — but breaks silently at the moment the value *doesn't exist yet* (mixer-ui-redesign: duck-trigger dropdown before any duck is enabled — no live `DuckSpecConfig.trigger` and, post-removal, no draft either to seed the dropdown's selection from). That gap needs an explicit default-value decision made consciously at the point the value is first created (here: enabling the checkbox seeds the trigger with the first other group's name), not left as an implicit blank — surface it as a judgment call to the user rather than silently picking one.
- 2026-07-21 [review] When a user's verbal answer to a design judgment call implicitly assumes a structure that isn't guaranteed to exist (mixer-ui-redesign: "drag between group footers only" assumed an implicit catch-all group that may not be configured), cross-check against the actual visual reference/mockup before locking it in — the mockup's own Master-column footer resolved it cleaner than the literal answer would have.
- 2026-07-22 [review] When a UI redesign relocates an existing always-visible control behind a new collapsed/gear panel, and the mockup doesn't dictate that specific control's placement (only that a gear icon exists), don't infer placement from symmetry with sibling controls ("other advanced settings hide behind a gear, so this one should too") and just log the decision — surface it as a judgment call before implementing, same as an explicitly-ambiguous contract gap already gets surfaced. Symmetry reasoning is real signal, but it's still a discoverability-affecting guess about a control the user may reach for often (mixer-ui-redesign: Master's Mute checkbox) — caught in review here, confirmed correct after the fact, but should be asked before code, not after.

- 2026-07-22 [review] A drift-check `## Links` changelog entry ("§X eliminated/superseded") is a note about the change, not the change itself — the spec's own body text (§2.2 non-goals, §9.5, the §13 phase table, §15 open questions) needs the same edit, or a reader who trusts the body over the changelog gets a stale architecture picture. Caught here: process-loopback-capture's Links entry correctly says "§9.5 eliminated, no virtual driver dependency of any kind," but §9.5's body, §2.2, §13's P1 row, and open question #2 still describe BYOD/VB-CABLE as v1's active requirement. Treat a drift-check pass as incomplete until the named sections are actually edited, not just logged.

## Implementation Craft

- 2026-07-19 [implementation] When a blueprint's contract references a type documented under a sibling component that the build order constructs later, relocate the type to the earlier-built *consumer* rather than reordering the build or fully decoupling — same interface-at-consumer idiom as port traits, extended to config/DTO types. Recurred 2026-07-20 (P3's `MatchRule`/`GroupRules`, contract text put them under `control` but `engine::routing`'s own API needed them) — worth treating as a standing rule to check for, not a one-off.
- 2026-07-19 [implementation] For unfamiliar or fast-moving external crate APIs (major-version churn), verify exact signatures by writing the call and reading the real compiler error, not from memory or pre-written notes — notes can predate a dependency's breaking change; the compiler is ground truth. When a crate's own docs aren't browsable in-session, this is also faster than hunting for docs.
- 2026-07-19 [implementation] Before committing to a dependency's latest major version, check for accidental package-name collisions in its transitive tree (an external crate can happen to share your own workspace crate's name) — breaks `cargo build/test -p <name>`. Pinning to an older minor that matches already-written internal documentation can dodge both the collision and an API rewrite at once.
- 2026-07-19 [implementation] RAII guards for OS thread-affine resources (COM apartments, etc.) can't be struct fields on a type required to be `Send + Sync` — use a lazy per-thread `thread_local!` initializer called at the top of every method that touches the resource instead.
- 2026-07-19 [implementation] Real-time thread orchestration functions (open ports → compute timing → build the mixer → spawn N thread kinds → assemble a handle) accrete responsibilities fast and quietly cross the parameter-count/size thresholds — `#[allow(clippy::too_many_arguments)]` on a hot function is a signal to extract a context struct right then, not a thing to suppress and revisit later. Caught one review cycle later than it should have been.
- 2026-07-19 [implementation] A design's L3 interaction chain can name components a later, unbuilt phase owns (e.g. "gain → DspChain → duck → matrix → SRC" when DspChain/duck are P5 and not yet in the repo). Check the actual current code before implementing, not just the blueprint text — slot the new stage where the future component will insert, rather than stubbing a hook for it or blocking the whole feature on the other phase landing first.
- 2026-07-19 [implementation] Before threading a new field through a domain type (e.g. adding `layout` to `Format`), grep for every site that constructs that type raw from an external source — duplicated derivation logic (three places independently rebuilding `Format` from a raw `WAVEFORMATEX*`) is invisible in a blueprint that names only one of them, and adding new parsing logic to all three independently triples the chance of getting risky unsafe code wrong in exactly one spot. Consolidate to one shared function first, then add the field.
- 2026-07-19 [implementation] Existing `#[ignore]`d real-hardware tests are a normal implementation-time validation step for platform-boundary features, not optional polish saved for later — running one against real hardware mid-implementation caught in seconds what a mock structurally cannot (e.g. confirming a mask-decode path against the actual device that motivated the feature), turning a "should work" into a "confirmed on the real device."
- 2026-07-20 [implementation] windows-rs's `#[implement]` macro (COM callback interfaces, e.g. `IMMNotificationClient`) expands to absolute `::windows_core::...` paths — these only resolve if `windows-core` is a *direct* Cargo dependency at the version `windows` pins internally, not merely available transitively through `windows`. A transitive-only dependency fails with `E0433 could not find windows_core`, with no hint pointing at the fix.
- 2026-07-20 [implementation] A struct that owns windows-rs COM interface handles (e.g. `IMMDeviceEnumerator`, `IMMNotificationClient`) needs an explicit `unsafe impl Send` to live behind a `Mutex` on a `Send + Sync`-bound type — windows-rs interface wrappers are `!Send` by default. Sound exactly when every thread touching COM in the crate already joins one apartment (MTA) first via a shared `ensure_initialized`-style guard; reuse that existing safety argument rather than re-deriving it per type.
- 2026-07-20 [implementation] An in-repo "reference pattern" comment for undocumented/hand-declared COM (even one that explicitly warns "verify against the real source before use") can still be wrong on the exact thing it warns about — a sketch in this repo's own implementation-notes.md showed 2 real methods for `IPolicyConfig` where the actual interface (verified via a live fetch of EarTrumpet's source) needs 12 own vtable slots (8 unused + 2 more unused + 2 real). Treat any such sketch as a pointer to go verify, never as the verified answer itself, even when it says so.
- 2026-07-20 [implementation] Hand-declaring a WinRT/`IInspectable`-derived COM interface (`windows-core`'s `#[interface]` macro) when the crate version has no generated `{Parent}_Impl` trait for that base (true for `IInspectable` in windows-core 0.62): declare the trait as `: IUnknown` instead and manually placeholder-slot the base interface's own extra methods ahead of the real ones (`IInspectable` adds 3: `GetIids`/`GetRuntimeClassName`/`GetTrustLevel`) — produces an identical vtable layout, since ABI correctness depends on memory layout, not which Rust trait hierarchy describes it.
- 2026-07-20 [implementation] Before writing code against a fast-moving GUI/native-integration crate (tray-icon/muda, global-hotkey, tao, eframe), a few targeted WebFetch docs.rs lookups for the exact constructor signatures, thread-affinity requirements, and trait method names paid for themselves directly — four such crates in one session compiled clean or near-clean on the first attempt, versus the multi-round compile-fix churn every un-verified guess produced elsewhere. Worth the lookup specifically for native-integration crates, where API shape and platform requirements (not just names) are easy to get wrong from memory.
- 2026-07-22 [implementation] When the fast-moving GUI/native-integration crate needing API verification is already a workspace dependency, grep its real source directly from the local cargo registry cache (`~/.cargo/registry/src/*/crate-version/`) instead of a WebFetch to docs.rs — faster, works offline, and exact-version-matched by construction (no risk of reading a newer/older API than what's actually pinned in Cargo.lock). Used here to verify egui 0.35's `dnd_drag_source`/`dnd_drop_zone`/`Slider::vertical`/`ComboBox::from_id_salt`/`AsIdSalt` before writing any call (mixer-ui-redesign) — compiled clean on the first attempt across all three implementation layers. Reserve the WebFetch approach for crates not yet vendored locally.
- 2026-07-20 [implementation] A new block-based FFT convolution algorithm (uniformly-partitioned overlap-save / frequency-delay-line, spatial-audio's `PartitionedConvolver`) is fully verifiable through pure unit tests with hand-derived expected values — unit-impulse identity, a 2-tap moving-average closed form, and a multi-partition impulse reconstruction (impulse longer than one partition) — before any real audio device or even a full `Spatializer` is involved. Caught the exact one-partition output delay and multi-partition FDL-shift indexing correct on the first pass because the math was worked out by hand against the test, not just "sounds about right."
- 2026-07-20 [implementation] Wrapping a fixed-block-size algorithm (FFT convolution partition size B) behind a per-call arbitrary-length `process(input, output) -> same length` contract: prime the output ring with B silence samples at construction, then push/pop exactly one sample per input sample fed (running a block whenever the input accumulator fills). Gives a provably-bounded backlog (max B+1, proven by the invariant "produced count after n samples fed is `B*(1+floor(n/B))`, always >= n") with a trivial correctness argument — reusable for any block processor that needs a streaming per-sample-call API without letting callers deal in fixed block sizes.

- 2026-07-20 [implementation] Flipping a binary to the Windows GUI subsystem (`#![windows_subsystem = "windows"]`) silently voids every `eprintln!`/`stderr` diagnostic and `exit(1)` message — there's no console to receive them, so a double-clicked app fails invisibly. The subsystem flip and an alternate diagnostic surface (file logger + panic hook → native dialog) must land in the *same* change, never as a follow-up; gate the flip behind `cfg(not(debug_assertions))` so dev builds keep the console. Same runtime-only-surfacing shape as the eframe/COM apartment gotcha — no unit test catches it.
- 2026-07-21 [implementation] A windows-rs type with a *real* (not hand-declared) `Drop` impl can still cause memory corruption when you manually construct one holding a pointer the `Drop` impl doesn't expect — `PROPVARIANT`'s `Drop` calls `PropVariantClear`, which for `VT_BLOB` calls `CoTaskMemFree` on `blob.pBlobData`; a blob pointer into a Rust-`Box`-owned struct (not `CoTaskMemAlloc`-allocated) gets freed through the wrong allocator the moment the value drops. Fix is `ManuallyDrop`-wrapping the *outer* value itself, not just an inner union field already wrapped for the same reason — confirmed by comparing against a real working implementation (`wasapi-rs`'s process-loopback activation) that double-wraps for exactly this. Caught by an actual `STATUS_HEAP_CORRUPTION` crash on the first real-hardware run, not by any static check. Generalizes: any manually-constructed windows-rs union/struct that owns a pointer needs its *whole* value's `Drop` behavior audited, not just the specific field being set.
- 2026-07-21 [implementation] A reference sample's offhand comment ("could also call X instead") is not verification that X works — Microsoft's own `ApplicationLoopback` sample notes `GetMixFormat` as an alternative to its hardcoded capture format, but calling it on a process-loopback-activated `IAudioClient` returns `E_NOTIMPL` on real hardware: that specific client type doesn't support format negotiation at all, unlike every other `IAudioClient` this codebase opens. Caught in seconds by running the `#[ignore]`d real-hardware smoke test against a live pid before shipping the assumption — treat any "or you could" aside in reference material as unverified until actually run, same as a hand-declared vtable sketch.

- 2026-07-21 [review] For config/script written in a build-tool DSL this environment can't compile-check (Inno Setup `.iss`, and by extension CI YAML, other installer/packaging DSLs — no toolchain installed to run it against), a live docs lookup before finalizing isn't optional polish the way it might be for a compiled language — it's the *only* verification available, since there's no compiler to eventually catch a wrong directive/value. Caught one real question this way (`ArchitecturesInstallIn64BitMode`'s valid values) that turned out already correct, but would have shipped as an unverified guess either way without the lookup. **Recurred immediately once the toolchain became available**: docs-lookup verification is a *substitute* for compiling, not equivalent to it — a real `iscc` compile the same session caught a flag (`runasoriginaluser` assumed valid in `[UninstallRun]` by symmetry with `[Run]`) that no doc skim had actually been run against for that specific section, and further investigation showed no such flag exists there at all (a genuine Windows/UAC platform limitation, not just wrong Inno syntax) — `runascurrentuser` is the closest available, with a real accepted-tradeoff edge case (standard user elevating with different admin credentials under-cleans HKCU on uninstall). When the real toolchain is available even once, compile against it before treating a docs-lookup-verified script as done.

## Quality Signals

- 2026-07-20 [review] When a log/telemetry line needs a derived scalar from a domain object that's already constructed for real elsewhere in the same code path (spatial-audio's `log_channel_conversions` called `HrirSet::embedded(rate)` a second time, off the same rate, purely to read `.taps()` — `Render::build`/`Mixer::new` had already built the real one for the actual `Spatializer`), expose a cheap pure accessor for the derived value instead of reconstructing the whole object. Correctness is unaffected (both calls compute the same thing), but it's wasted work and a coupling smell — the log function reaching into full domain construction just to describe a decision another function already made.

- 2026-07-19 [review] In a fallback/precedence table written as `match` arms, an unguarded arm always wins once its pattern matches — it silently bypasses a shared catch-all that sibling arms fall through to correctly. Inconsistent guarding across otherwise-parallel arms (3 of 11 speaker-fold rules unguarded, 8 correctly guarded) let one function's own documented "never lose audio" contract quietly break for a subset of valid inputs. When reviewing or writing this pattern, check every arm for the same guard-vs-unguarded shape, not just a sample of them.
- 2026-07-20 [review] When a param-threshold refactor (extract a context struct once a function's parameter list crosses the too-many-arguments line) gets applied to one of two structurally-mirrored functions, the sibling is easy to leave un-refactored — the reviewer catches it, not the author, because each function individually still "looks fine" in isolation. Do a symmetry pass across mirrored functions (e.g. capture-side vs render-side thread loops) at the end of a change, not just a per-function threshold check.
- 2026-07-20 [review] Multiple faults/events landing in the same poll-loop tick that each independently trigger a full rebuild/re-sync (rather than batching into one) is an easy-to-miss N-times-the-cost edge case — worth explicitly documenting as an accepted tradeoff at the point of implementation (same style as this codebase's already-documented concurrent-rebuild race), so a later reader doesn't mistake it for an oversight.
- 2026-07-20 [review] A test asserting "signal A is attenuated relative to reference B" on a value that's spread across several decaying taps (a spatial-audio HRIR's head-shadow kernel, an envelope tail, any short FIR spread) must compare peak/max magnitude, not sum-of-absolute-values — summing several taps each close to the per-tap attenuation can add up to more than one single-tap reference value even though every individual sample is correctly attenuated. Caught by the test itself failing (`a_right_side_position_delays_and_attenuates_the_left_ear`), not by inspection — worth checking this shape (sum vs peak) whenever a test compares "spread energy" against "single-sample reference."

## Reliability

- 2026-07-21 [review] A picker/onboarding UI that lets a user independently pick two config fields referencing device/resource names (e.g. simple-launch's onboarding `bus_endpoint` picker + a "default output" fallback for `output_device`) must actively exclude the case where both resolve to the same underlying resource, whenever a downstream step assumes the two are disjoint (here: `engine::graph::resolve` requires `bus_endpoint` to classify `Bus` and `output_device` to classify `Physical` — same name for both can never satisfy both). Don't just default one field to "whatever's already selected/default" and assume they won't collide; the collision is a realistic real-world case (a user who already set a virtual cable as their OS default output), not a hypothetical edge case, so the picker needs an explicit exclusion check, not silent hope.
- 2026-07-21 [review] A shared UI-state mutex that a GUI render loop locks every frame (e.g. `ui.rs`'s per-frame `self.ui.lock()`) must never stay held across a blocking OS/COM call made from another thread (e.g. a dispatcher's `sys.enumerate()` re-check inside `set_current`) — the render thread stalls for the call's duration even though nothing deadlocks. Same shape as the already-logged "don't call back synchronously into the API delivering a notification" and "GUI-thread/COM apartment" reliability rules: read what you need under a short lock, do the blocking work outside any lock, then re-lock only to write the result.
- 2026-07-21 [review] **Third occurrence of the same shape** (see the two entries above): `engine::runtime::CaptureControl::apply_capture_sources` held `self.running`'s lock across `AudioSystem::open_process_capture` — a blocking WASAPI/COM activation call — even though the function reads as a plain diff-and-open helper, not obviously "GUI code" or "notification callback" the way the two prior instances were. `MockSystem`-backed tests never caught it (the fake returns instantly). Generalize the check: any new method that calls into an `AudioSystem`/port-trait method must be audited for whether it executes while holding the running-graph mutex or any other lock shared with `stats()`/`apply_params`/`rebuild`/etc — not just code that visibly touches a GUI frame loop or a device-notification callback. Ask "what else locks this same mutex, and for how long would this callee's real (non-mock) implementation actually block?" for every new lock-guarded call site, regardless of how mundane it looks.
- 2026-07-21 [review] A genuinely async completion-callback COM API (`ActivateAudioInterfaceAsync` + `IActivateAudioInterfaceCompletionHandler`, process-loopback-capture) needs a *timeout* on the wait from the very first implementation, not added later — every other WASAPI call in this codebase so far has been synchronous, so there was no existing async-wait pattern to copy from, and the first draft waited on the completion condvar unconditionally. Combined with the lock-scope finding above, an unbounded wait on a call that never completes (stuck driver, COM edge case) would have frozen the whole engine's control surface, not just the one capture attempt. Any *new* async-callback-shaped platform API introduced into this codebase should get a bounded wait (`wait_timeout`, erroring on expiry) as part of the first draft, not a follow-up.

- 2026-07-18 [design] For unreliable/undocumented APIs: first failure → flag + single notice + skip further calls; retry only on deliberate user action. No retry storms, no silent spam.
- 2026-07-18 [design] Cross-feeding computations: fix producer-before-consumer order within a cycle/block and reject dependency cycles at validation time — determinism by construction, not runtime checks.
- 2026-07-19 [reliability] Real hardware/OS smoke tests (marked ignored, run explicitly during development, not in normal CI) catch API-shape and integration mistakes that mocks structurally cannot — worth writing per platform-boundary component even when the permanent suite can't run them unattended.
- 2026-07-20 [reliability] OS notification/event callbacks (COM `IMMNotificationClient` and the same shape elsewhere — GUI event handlers, signal handlers) must never call back synchronously into the API that's delivering the notification (e.g. `IMMDeviceEnumerator::GetDevice`/`EnumAudioEndpoints`/`GetDefaultAudioEndpoint` from inside an `IMMNotificationClient` method) — the platform docs usually warn about this explicitly (MSDN's `IMMNotificationClient` remarks did), and violating it risks deadlocking a thread the OS shares across the whole process, not just this app. If the callback needs data that requires calling back in, capture the minimal identifier and defer the real work to a spawned thread or an existing consumer loop; return from the callback immediately. Caught in review before shipping, not by a test — this class of bug doesn't reproduce reliably enough for a unit test to catch.
- 2026-07-20 [review] Integration tests that drive a background poll thread through a fake port (e.g. emitting a mock device event) need the thread to have reached its subscription/setup point first — a fixed `sleep` before emitting is a latent flakiness seed on a slower CI runner, not a real synchronization guarantee. Prefer a readiness signal from the fake (e.g. record that a subscriber attached) over a fixed delay when the test is otherwise deterministic.
- 2026-07-20 [review] A COM callback registered via a `RegisterX`/`UnregisterX` pair (e.g. `IAudioSessionControl::RegisterAudioSessionNotification`, `IAudioSessionManager2::RegisterSessionNotification`) needs an explicit `Drop` calling the matching `UnregisterX` — the callee `AddRef`'s the callback on registration, so dropping only the local handle leaks the registration on the OS side indefinitely, it does not unregister itself. Recurred once already: `DeviceMonitor` (P2) got this right via an explicit `Drop`, but `WasapiSessions` (P3) missed it for a near-identical shape until caught in review. Treat every `RegisterXNotification` call as needing its `Drop`-time `UnregisterX` counterpart verified, not assumed present just because the pattern looks RAII-shaped.
- 2026-07-20 [implementation] Mixing a GUI framework's required-thread initialization (e.g. `eframe`/`winit` needing `OleInitialize`/STA on whichever thread calls `run_native`) with any other library that touches COM (WASAPI, etc.) on that same thread only surfaces as a runtime panic (`RPC_E_CHANGED_MODE` on apartment-mode conflict) — no mock or unit test can catch this, since it's a real OS/thread-apartment interaction between two libraries' independent COM usage.
