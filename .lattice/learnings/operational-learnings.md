# Operational Learnings

Experiential patterns from practice. Complements standards (what should be) with experience (what we keep learning).

## Design Patterns

- 2026-07-18 [design] Interface-at-consumer for OS-API seams — when a crate wraps platform APIs, define port traits in the consumer crate, not the wrapper; otherwise the wrapper's platform deps break cross-platform tests.
- 2026-07-18 [design] Live control of RT systems splits cleanly: param changes via lock-free commands, structural changes via supervisor rebuild — the RT no-alloc/no-block rule decides which side a change falls on.
- 2026-07-18 [design] Keep third-party transport types (ring/channel libs) out of port trait signatures — pass slices, own the transport in the orchestrator; mocks stay trivial and the lib stays swappable.
- 2026-07-18 [design] Model feedback loops as pure `tick(measurements) -> commands` — unit-testable with synthetic curves, no threads or OS in the test.
- 2026-07-18 [design] Start control loops with only the directly-held error signal; add feedforward inputs (extra sensors/APIs) only when evidence shows slow convergence.
- 2026-07-18 [design] Extend an existing port facade with a method instead of adding a new single-consumer trait — a second abstraction needs a second consumer. Amended 2026-07-18: facade growth stops at concern boundaries — must-work and may-fail/feature-gated surfaces get separate traits even with one consumer each. Amended 2026-07-21: when the new capability is backend-specific and most implementors (mocks, other backends) have nothing meaningful to do with it, give the trait method a default no-op body rather than making every implementor add one — `AudioSystem::set_bus_match` (simple-launch.md) reached `WasapiSystem` without any change to `MockSystem` or its test call sites. Stays dyn-safe (no generics in the signature) and keeps the change's blast radius to the one backend that actually needs it.
- 2026-07-18 [design] Manage external mutable state (OS prefs, remote config) as desired-state reconciliation with an applied-map — idempotent, re-runnable on any change, never rewrites what's already applied.
- 2026-07-18 [design] Trace latency through the whole mutation path before committing to single-funnel designs — file-watcher round-trips are 100s of ms; interactive controls need a fast path carrying the same value, source of truth unchanged.
- 2026-07-18 [design] Machine edits to user-editable files: semantic edit enum → format-preserving editor → atomic rename → echo suppression, as one package. Never raw-text patching, never re-serialize.
- 2026-07-18 [design] When a later design level invalidates an earlier decision, revise it explicitly with a logged revision entry — not silently. Keeps the decision log trustworthy.
- 2026-07-18 [design] Structural changes to RT-owned state: pre-build off-thread → pointer-swap via command → return old state for off-thread drop. Glitch-free, alloc-free on the hot path.
- 2026-07-18 [design] Processing that spans entities (sidechains, cross-feeds) doesn't fit per-entity pipeline traits — hoist to the orchestrator instead of widening the trait with params most stages ignore.
- 2026-07-18 [review] After designing multiple features against shared contracts, run a dedicated cross-blueprint seam review — event fan-out, channel producer counts, id stability across rebuilds, thread pacing. Per-feature reviews structurally miss these.
- 2026-07-19 [design] When implementation drops a spec'd domain field (e.g. `Format.layout`), capability silently narrows — the hard-fail surfaces at real-hardware boundaries, not in mocks, because mocks are built with matching formats. Diff implemented value objects against the spec's domain model when a gap appears.
- 2026-07-19 [design] When a feature's purpose is removing a failure class, make its core constructor infallible — fold unknown inputs with normalization rather than reintroducing strict errors at the edges (channel-mixdown: unknown speaker positions fold at −3 dB instead of erroring).
- 2026-07-19 [design] For format/audio conversion design, research the governing standard first (ITU-R BS.775, RFC 7845, FFmpeg's matrix model) — the standard's static-matrix formulation made RT-safety (pre-allocated, pure, infallible) fall out for free.
- 2026-07-20 [design] When a design revision names a component as owning a mutating handle for a stated purpose (e.g. "EventPump calls routing.update_topology on structural events"), verify the underlying event stream can actually deliver the signal that purpose depends on before implementing it literally — here no `EngineEvent` variant signaled "routes changed," so a polling read-only view (`RoutingReader`) was strictly more correct than the event-driven design the revision sketched.
- 2026-07-20 [design] For perceptual-audio features, check whether ecosystem libraries' moving-source generality is actually needed before adopting one — fixed-position virtualization (spatial-audio) collapses to per-channel static convolution, far simpler and RT-safer than general 3D spatializers (`hrtf` crate's sphere interpolation, click artifacts). Studying the commercial reference implementation (HeSuVi/Equalizer APO) is what revealed the collapse; same spirit as the research-the-governing-standard rule.
- 2026-07-20 [design] Adding an alternative processing path to an existing pipeline slot: model it as an enum replacing the existing field (`Render::Matrix | Spatial`) plus a widened retire type on the existing swap-and-retire channel — not a trait (two known variants, one consumer) and not a parallel field (two paths live, one dead). Reuses the swap/epoch/off-RT-drop machinery wholesale; downstream stages untouched.
- 2026-07-20 [design] An elevated machine-wide installer is the wrong actor for per-user state — config in `%APPDATA%` and autostart in the HKCU Run key belong to the *end* user, but the installer runs as admin. Hand config bootstrap + autostart to the app's own first-run (launched `runasoriginaluser`), keeping the installer to binary/shortcut/uninstaller only. Recurring Windows-packaging trap; also keeps a single reconcile path (the app already reconciles `set_autostart` every startup) instead of the installer and app both writing the Run key.
- 2026-07-20 [design] When a blueprint assumes fetchable external data (a measured HRIR set, a downloaded reference dataset, ...) and it turns out unreachable at implementation time (no network access this session), preserve the public API/contract shape and swap the *internal* construction strategy instead of blocking the feature or silently guessing — surface the tradeoff to the user first (spatial-audio's `HrirSet::embedded` ended up procedurally synthesizing ITD/ILD cues instead of decoding measured tables; every downstream contract stayed identical).

- 2026-07-22 [design] When a design pivot swaps the underlying OS primitive for a capability (WASAPI per-app redirect → process-loopback capture), explicitly audit what the OLD primitive gave for free that the NEW one doesn't — not just whether the new one satisfies the capability list as written. A redirect silences the original path inherently (it moved); a tap/capture does not. Nothing in process-loopback-capture's Level 1 named "silence the original" because under the old model it wasn't a feature, it was a side effect of how redirect worked — the gap (session-mute-on-capture) only surfaced from actually listening to real audio, since the capture→mix→render pipeline's own tests have no way to model "is the untouched original also still audible outside the system under test."
- 2026-07-21 [design] When production instability keeps tracing back to the same architectural area, question the spec's own stated *rationale* for that area, not just the implementation built on top of it — a platform-API claim ("no supported per-session PCM capture") can be outdated or simply wrong even when it was accurate at write time, superseded by a later OS release the original author didn't know about. Caught here only because the debugging session kept failing to root-cause instability in an undocumented-API-based design; re-deriving from first principles ("is this claim even still true?") found a documented replacement API that eliminated the whole fragile surface rather than patching around it.
- 2026-07-21 [design] Cloneable `*Control`/`*Reader` handles (`RoutingHandle::reader() -> RoutingReader`, `EngineHandle::capture_control() -> CaptureControl`) are this codebase's established idiom for giving a second thread safe access to RT-adjacent shared state without transferring single-owner resources (a `JoinHandle`, a `Receiver`) that make the owning type itself non-`Clone`. Reach for this by name — a small wrapper struct cloning only the `Arc<Mutex<..>>`/`Arc<..>` fields a caller actually needs — instead of re-deriving the shape from scratch each time a new cross-thread capability is needed.
- 2026-07-21 [design] When a prior decision names a specific missing capability as its reason ("no device-enumeration read model to back a picker"), check whether a later feature actually built that capability before layering new UI on the old workaround — reverse the old decision explicitly (mixer-ui-redesign's dropdown-backed pickers reversing app-shell.md's draft-then-commit text-field decision) rather than leaving both patterns coexisting. **Amended 2026-07-25: reverse a prior decision by checking its stated *reasoning*'s premise, not its conclusion.** `responsive-ui-refinement` decided Master's column gets no gear icon — but the recorded reason was "nothing left to hide behind one once mute moves here", not "Master should never have a settings page". routing-truthfulness needed somewhere to show the exclusion list, which creates something to hide, so the premise is gone and the conclusion falls with it: a clean reversal, not a contradiction, and the replacement mirrors the `Screen::GroupSettings(name)` pattern that already exists rather than inventing a second navigation shape. This check only works if the decision log records *why* — a log of bare conclusions makes every reversal look like a contradiction and pushes designers toward silently coexisting patterns instead.
- 2026-07-21 [design] A discrete-selection widget (dropdown/combo) never needs the draft-then-commit pattern free-text fields need — only typing has in-progress state worth protecting. When a text-field-plus-commit-button becomes dropdown-backed, drop the draft state entirely rather than carrying the pattern over out of habit.
- 2026-07-22 [design] Dropping a draft field in favor of reading a dropdown's current value fresh each frame (the pattern above) works fine once the underlying value already exists — but breaks silently at the moment the value *doesn't exist yet* (mixer-ui-redesign: duck-trigger dropdown before any duck is enabled — no live `DuckSpecConfig.trigger` and, post-removal, no draft either to seed the dropdown's selection from). That gap needs an explicit default-value decision made consciously at the point the value is first created (here: enabling the checkbox seeds the trigger with the first other group's name), not left as an implicit blank — surface it as a judgment call to the user rather than silently picking one.
- 2026-07-21 [review] When a user's verbal answer to a design judgment call implicitly assumes a structure that isn't guaranteed to exist (mixer-ui-redesign: "drag between group footers only" assumed an implicit catch-all group that may not be configured), cross-check against the actual visual reference/mockup before locking it in — the mockup's own Master-column footer resolved it cleaner than the literal answer would have.
- 2026-07-22 [review] When a UI redesign relocates an existing always-visible control behind a new collapsed/gear panel, and the mockup doesn't dictate that specific control's placement (only that a gear icon exists), don't infer placement from symmetry with sibling controls ("other advanced settings hide behind a gear, so this one should too") and just log the decision — surface it as a judgment call before implementing, same as an explicitly-ambiguous contract gap already gets surfaced. Symmetry reasoning is real signal, but it's still a discoverability-affecting guess about a control the user may reach for often (mixer-ui-redesign: Master's Mute checkbox) — caught in review here, confirmed correct after the fact, but should be asked before code, not after.

- 2026-07-22 [design] Before locking a UI/UX redesign decision (a new navigation pattern, an input-widget swap), research 2-3 comparable real apps' actual shipped patterns rather than designing from intuition alone — this session's Level 1 (gear icon → separate settings screen; checkbox → icon-based mute) was directly shaped by SoundSource's gear-opens-separate-Settings-window pattern and EarTrumpet's icon-based (not checkbox) per-app mute, found via a few targeted searches before drafting capabilities.
- 2026-07-22 [design] When independent per-key boolean toggles (`HashMap<Key, bool>`, e.g. per-group "is this panel expanded") become mutually-exclusive by a new design intent (only one panel/page ever visible at a time), replace the map with a single enum tracking which one is active — an enum has no representable invalid state (two keys both `true` at once), where the map allowed one even if the UI happened to never actually trigger it (responsive-ui-refinement's `Screen::{Mixer, GroupSettings(String)}` replacing `advanced_open: HashMap<String, bool>`).
- 2026-07-22 [design] Before adding a new icon-style glyph character to an egui UI, check whether it falls in a Unicode range already proven to render in this codebase's font stack (e.g. ⚙ U+2699, already shipped) rather than assuming a new one (e.g. 🔊/🔇, emoji-range) will render the same way — emoji-range glyphs risk a blank tofu-box with no fallback font. When unsure, prefer a custom-painted vector icon (`egui::Painter`) over guessing a new glyph will render correctly.

- 2026-07-22 [review] Reproducing an engine-internal positional assignment on the UI side is fragile — it silently diverges the moment the authoritative code applies a filter the UI can't see. Level-meters' master column re-derived the `OutputId`→device-name order from `snapshot.groups` (distinct output devices in group order), matching `engine::graph::resolve`'s own assignment — except `resolve` skips **parked** groups (drift-and-recovery), so during a device-loss episode every device label after a parked group shifted by one. The meter *values* stayed correct and in engine order; only the reproduced *labels* were wrong, and only in the transient parked state — the hardest case to notice, invisible to every non-degraded test. Fix: when the UI needs a mapping another layer already computes with logic the UI can't fully mirror, expose it from the authoritative side (a small static `EngineStats.output_names`, populated in `resolve` as each id is assigned) rather than re-deriving it. Same family as the "check whether a later feature already built the capability before layering UI on the old workaround" learning — prefer the source of truth over a lookalike reconstruction.
- 2026-07-22 [review] A drift-check `## Links` changelog entry ("§X eliminated/superseded") is a note about the change, not the change itself — the spec's own body text (§2.2 non-goals, §9.5, the §13 phase table, §15 open questions) needs the same edit, or a reader who trusts the body over the changelog gets a stale architecture picture. Caught here: process-loopback-capture's Links entry correctly says "§9.5 eliminated, no virtual driver dependency of any kind," but §9.5's body, §2.2, §13's P1 row, and open question #2 still describe BYOD/VB-CABLE as v1's active requirement. Treat a drift-check pass as incomplete until the named sections are actually edited, not just logged.

- 2026-07-22 [design] A new read-only display/telemetry feature (level meters) should attach to the codebase's existing RT-atomic → `EngineStats` → poll path rather than invent new transport: the mixer (domain) stays transport-free, exposing a plain accessor (`group_peak`/`output_peak`, mirroring `output_limiter_engaged`); the engine's mixer-thread loop reads that accessor after each tick and stores into a `RunningGraph` atomic (f32→bits `AtomicU32`, exactly like the already-shipped `duck_depth_db`/`limiter_engaged`); the UI pulls fresh every frame via a `Clone`-able `StatsReader` handle (the same `*Reader` idiom as `RoutingReader`, line 31). The whole feature became "one more field on three existing structs + a widget" because nothing new about the data path had to be designed — check for this ride-the-existing-telemetry-path option before adding any push channel or per-frame event for a value that's fundamentally just "current RT state, sampled." Ballistics that need smoothing live in a pure domain value object (`PeakMeter`, same per-frame-advance rule as the env-follower) so they stay unit-testable off-thread; pure display niceties (peak-hold dot) stay UI-side with no domain footprint.

- 2026-07-22 [design] Scoping an existing **global** control down to a **per-entity** one: re-audit every collaborator the global implementation was allowed to ignore *because* it was global. Master mute could leave the duck sidechain untouched — with everything muted, a muted group still driving a duck trigger had no audible consequence — but per-group mute makes that exact code path a real bug (muting Chat would leave Game permanently ducked by audio the user can't hear). The per-group version isn't "the global one with an index added"; it's the first time the surrounding pipeline can observe the silenced state while other signal is still flowing. Same family as the 2026-07-22 entry about auditing what the *old* primitive gave for free after a pivot — both are "the change looks like a narrowing, but it re-opens assumptions the wider version got to make."
- 2026-07-22 [design] Enforce a "rebuild resets X" rule by **omitting X from the build spec**, not by adding a clearing step. Per-group-mute-solo's `GroupSpec` deliberately carries `mute` but no `solo`, so a rebuilt mixer starts every group unsoloed by construction. An explicit `clear_solo()` call is something a future rebuild site can forget to make; a field that doesn't exist can't be populated by accident. Applies whenever session-only state coexists with persisted state in the same entity — let the construction path carry only what should survive.
- 2026-07-22 [design] Before reusing an existing monotonic counter as a change signal, grep **every** site that bumps it. `Epoch` looked like a free "the mixer was rebuilt" signal — there's even a `rebuild_bumps_the_epoch` test naming exactly that — but it also bumps on DSP chain swaps (runtime.rs:1277), so adopting it would have silently cleared session-only solo state on an unrelated EQ edit. A counter's *name* and its most prominent test describe one of its bump sites, not the set. When the existing counter over-triggers, the fix is a new counter owned by the layer that actually knows the fact (here the app shell, which calls `rebuild` at exactly two places) — the same "prefer the authoritative source over a lookalike" instinct as the level-meters `output_names` finding.

- 2026-07-22 [design] **A widget's `Sense` decides which gestures are even possible — check it before designing a gesture onto it.** Two occurrences in two sessions: egui's `Slider` allocates with `Sense::drag()` (slider.rs:655), so `Response::double_clicked()` is permanently dead on it and db-faders' double-click-to-unity could never have fired; `dnd_drag_source` returns a drag interaction unioned with a hover-only `ui.label` (ui.rs:2677), while `Popup::context_menu` opens on `secondary_clicked()` (popup.rs:248), so session-search's right-click assign menu could never have opened. Both were specified as ordinary gestures and both were caught only by reading the widget's source at design time. The fix is identical each time — allocate your own `ui.interact(rect, id, Sense::click())` over the widget's rect. Generalizes past egui: a gesture is only available if the underlying widget's input mask admits it, and that mask is rarely in the docs.
- 2026-07-22 [design] **Verify a backlog item's premise against the code before designing to it.** The UX roadmap said the faders had "no number, no numeric entry"; both already existed, because `egui::Slider::show_value` defaults to `true` and the value box is click-to-edit. The item named the wrong gap — the real one was the unit, the taper, and the unity reset. Recurred in the same batch: the roadmap called the EQ "one band per stage" when `ParametricEq` already cascades every configured band and only the *edit set* was missing. Backlog entries describing a UI deficiency are written from the outside, from memory of using the product; grounding routinely finds the feature is smaller in one dimension and larger in another. **Amended 2026-07-25: this extends to audit findings, including their proposed remedies.** An audit written by reading code is exactly as unverified as a backlog entry written from memory. Grounding the 2026-07-25 end-to-end audit before designing to it produced three corrections in one pass: B3's "make `read` drain until `GetNextPacketSize() == 0`" was already implemented (the real defect was only the caller's buffer size — a much smaller fix); B1 and B2 were listed as independent bugs but share a root through `period_frames()`, so fixing one changes the other's magnitude; and B8 is what makes B7 *dormant*, which the audit's own suggested ordering (B7+B8 as item 5, after everything else) would have shipped as a live regression. Re-derive an audit's causal claims, not just its symptom list.
- 2026-07-22 [design] **When a widget exposes formatter/parser/step/clamp hooks, make the widget's own value live in the unit the user thinks in.** Making the fader's slider value dB (rather than keeping it linear and formatting as dB) meant the formatter, parser, drag speed, range and clamping all operate in one unit and agree for free. The alternative needs a conversion inside every hook, and every hook is a fresh chance for them to disagree. The conversion then happens exactly once, at the widget's boundary.
- 2026-07-22 [design] **Where new `unsafe` lands is an architectural decision, and the invariant it threatens is usually unwritten.** `app` contained zero `unsafe` — not by stated policy, just by history — while all 49 unsafe blocks lived in `win-audio`. App-icons' Win32 icon extraction had two "obvious" homes: `app` (it's UI code) or `win-audio` (it already has the `windows` dep). Each would have quietly ended an invariant or stopped a crate's name from describing it. One `grep -c unsafe` across crates made the call for a third option (a new `win-shell` crate). Measure the concentration before placing a new capability class.
- 2026-07-22 [design] **Making a filter cross-cutting multiplies a UI's empty states.** Once session search spanned every chip zone instead of just the unassigned pool, "empty" split into "hidden by the filter" and "genuinely empty" — and without that distinction a filtered group would have told the user to drag an app into a group that already had one. The extra state is not optional polish; it is the direct cost of the filter's scope, and it needs a pre-filter occupancy input (`zone_had_chips`) that a naive post-filter count cannot provide.
- 2026-07-22 [design] **When a recommendation rests on "the error is small", compute it before recommending.** Graphical-eq's curve needs a sample rate; the proposal was to assume a nominal 48 kHz because "the curve is a guide" and the alternative was "plumbing". Both halves were wrong. A 20-line script showed the error reaches ~3 dB for a treble band on a 128 kHz device (1.34 dB at 10 kHz, 2.07 at 18 kHz, 2.97 at 20 kHz for a 15 kHz Q=1 +6 dB bell) — half the boost the user asked for — while the "plumbing" turned out to be one line against a `RunningGraph.group_formats` field that already existed and was already cloned under the lock. When a design tradeoff turns on a number (tolerance, precision, cost, error magnitude) and a script can produce that number in a minute, produce it rather than estimating its size.
- 2026-07-22 [design] **An edit or command that resolves its target by first-match silently breaks the moment the container can hold two.** `ConfigEdit::SetEqBand(group, band, spec)` locates its stage with `find_dsp_stage_mut(group, name, "eq")` — the *first* EQ stage. Correct while only one editor existed; silently wrong as soon as a per-stage editor can send from the second one, and the bug has no error path because it retunes a real band, just the wrong one. Whenever new UI can address multiple instances of a kind, audit every existing command that locates its target *by kind* rather than by index or id.
- 2026-07-22 [design] **CRUD-shaped edit sets over a small collection usually collapse to a single whole-collection replace.** Graphical-eq's `AddEqBand`/`RemoveEqBand`/`SetEqBands` became one `SetEqBands`: add is "current plus one", remove is "current minus one", the store rewrites the whole array regardless, and the caller already holds the current list from the snapshot. One variant, one store arm, one matcher entry instead of three of each — and a whole-list edit is atomic and immune to index races between frames. Recurred twice in the very next session (`SetDspChain` instead of add/remove stage sequences; no `RenameProfile`, which decomposes into `SetProfile` + `RemoveProfile` + `SetActiveProfile`). Check for it whenever an edit enum is about to grow a matched add/remove pair.
- 2026-07-23 [design] **When adding a save/restore layer over existing state, make the new thing a copy *of* the current representation rather than a replacement for it as the source of truth.** Profiles could have owned the values with `[[group]]` reduced to structural identity — conceptually tidier, and tempting. Keeping `[[group]]` as the live state and `[[profile]]` as copies written back into it meant the engine's read path, the config schema, `SUPPORTED_SCHEMA_VERSION`, and every existing user's file were untouched, and "no profiles configured" stayed byte-for-byte the current behaviour. The migration cost difference between the two shapes *is* the decision; the conceptual tidiness is worth far less.
- 2026-07-23 [design] **The first consumer that handles a heterogeneous *batch* of an existing command type reveals that dispatch knowledge was scattered across call sites.** Every UI site hardcoded which apply path an edit needs (`ui.rs` sends `EditStructure` for `SetGroupOutput`, `EditSpatial` for `SetSpatial`, `EditParams` for a gain). That worked while each site issued one kind of edit. A profile switch emits a mixed batch, so the knowledge had to become a value — `edit_path(&ConfigEdit) -> EditPath`. Note the first attempt at it was a bool (`is_structural`), which Level 4 exposed as too coarse because there are four apply paths, not two. Expect this whenever a new feature batches commands that were previously always issued singly, and expect the classifier to need more arms than the first guess.

- 2026-07-23 [design] **When a platform constraint forces a degraded in-app affordance, check whether the OS already ships the real thing before building the substitute.** Tray volume control was blocked by "a native menu cannot host a slider", and the planned answer was discrete level items — a coarse imitation of a fader nobody would prefer. Binding a group's gain to the Windows default endpoint volume instead gave continuous control, the native OSD, and the hardware volume keys, and it *deleted* the tray-volume work rather than adding to it (external-controls decision 1). The constraint was the signal: if the in-app version has to be degraded to exist, that is the moment to look outward for an existing control surface to bind to.
- 2026-07-23 [design] **Before mirroring app state into an OS-owned control, ask what else already consumes that value — and expect the answer to be "suspend", not "compensate".** An endpoint's volume is applied by the OS to everything rendered to that device, so mirroring it into a group's gain double-applies whenever the group's output *is* that device (50% → 25%). The useful half of the same fact: in exactly that configuration the volume keys already control the group natively, so the correct behaviour is to suspend the mirror and say why, not to divide it out (external-controls decision 4). Any two-way sync with a shared system resource needs "who else reads this?" answered before the sync rule is written.
- 2026-07-23 [design] **The data available at the *callback* boundary decides a port's unit, not the richest API available.** `IAudioEndpointVolume` exposes true dB (`GetMasterVolumeLevel`, `GetVolumeRange`), but `AUDIO_VOLUME_NOTIFICATION_DATA` carries only the scalar — and this codebase forbids calling synchronously back into the API that delivered a notification. Designing the port in dB would have required violating that rule on every volume key press. The port speaks position instead, which also sidesteps Windows' undocumented scalar→dB curve (external-controls decision 14). Design the contract from what arrives in the event, not from what the API could tell you if you asked it a second time.
- 2026-07-23 [design] **The cost of a cross-cutting visual change is set long before you make it, by whether widgets hardcode or delegate.** "Restyle the whole app" read as the widest item in the backlog and turned out to be a style pass with zero widget rewrites, because every custom-painted widget already read `ui.visuals()` (`extreme_bg_color`, `strong_text_color()`) rather than its own constants — only five hardcoded colours existed in the entire UI. The corollary is worth enforcing deliberately: keep new widgets reading from the central style so the *next* cross-cutting change stays cheap. Here that was made an explicit capability, because seven unbuilt features' widgets will otherwise each need retrofitting.
- 2026-07-23 [design] **Anything the app renders into someone else's surface must take its styling cue from that surface, not from the app's own settings.** The tray icon sits on the Windows taskbar, which has a light/dark theme independent of the app's preference; styling it from the app's theme makes it vanish whenever the two disagree — and a user who forces the app to the opposite theme is precisely the case that breaks (visual-identity decision 7). Generalizes to notifications, overlays, badges and embedded previews: the host context owns their appearance. Note the follow-on cost, which only appeared at Level 3: following an external surface's theme also means *observing* it, and a tray-only process has nothing positioned to watch — the honest options are new platform machinery, a polling timer, or accepting bounded staleness, and which one was chosen should be recorded rather than left implicit.
- 2026-07-23 [design] **The moment a UI concept becomes persisted, it stops being a UI type.** `AccentPreset` was drafted as an `app` type and had to move to `engine::graph` at Level 4, because `ConfigEdit` lives in `control` and `control` must never depend on `app`. This is the sharper form of the existing "Config type home" rule: **persistence, not subject matter, decides which crate owns a type.** A theme preference feels entirely like UI and is nonetheless a config type; the layer boundary catches it at contract-writing time if the contracts are actually written out, and at compile time if they are not.

- 2026-07-25 [review] **Two blueprints can each make a defensible decision and jointly kill a primary interaction — re-walk the shipped default configuration after anything changes what that default contains.** `mixer-ui-redesign` (2026-07-21) accepted "dragging a session back to Master only sticks if it was exact-name-assigned; a glob rule elsewhere re-matches it instantly" as a documented v1 limitation, and wrote a passing test asserting exactly that. `process-loopback-capture` (same week) made `*` the *recommended* catch-all mechanism, and first-run onboarding creates the default group with `match_rules: ["*"]`. Each decision is defensible alone. Together, on a fresh install: drag-to-unassign is a silent no-op, and Master's unassigned pool is permanently empty showing "All apps are routed" forever. Neither blueprint's own review could catch it, and the existing cross-blueprint-seam learning (2026-07-18) didn't either — that one looks for shared contracts, events, channel counts and id stability, and this seam was none of those, it was a **default value**. Add the check explicitly: whenever a feature changes what the default configuration *contains*, walk the product's primary gestures against that new default end to end, not against the empty or hand-built config the feature was designed on.
- 2026-07-25 [design] **When a UI gesture silently does nothing, check whether the vocabulary can express the intent before debugging the handler.** `resolve_drag_assign` was not buggy — it correctly emitted an empty edit batch, because the rule language could say "route X to group G" (an `ExactName` entry) but had no way at all to say "do not route X". Unassigning a glob-matched session has no representable answer, so an empty batch *was* the right output. The fix was a new precedence tier (a global exclusion list checked ahead of every rule), not a patched function. The give-away was a **passing test asserting the empty result on purpose** — a no-op that someone deliberately encoded is a vocabulary gap, not a defect. Ask "is there any value this function could have returned that would have been correct?" before treating a silent no-op as a bug.
- 2026-07-25 [design] **An audit or review's severity *ranking* is load-bearing on scope, and when it comes from arithmetic it must be measured before it sets that scope.** The 2026-07-25 audit called the 256-tap/128x sinc resampler "the second-largest CPU term after B5", derived from a 24.5 M MAC/s estimate — enough for it to be picked for a full design blueprint. A ~40-line scratch `cargo` project benchmarking the real pinned `rubato 0.15.0` at the real block size (608 frames, stereo, 25 s of audio) measured **0.285% of one core per group**, against B5's 0.7 ms spin per 10 ms poll = **7% of one core per routed pid** — 25x smaller, not second-largest. One run collapsed a planned five-level blueprint into two constants. Complements the existing "when a recommendation rests on a number, compute it" rule with its scoping consequence: estimated magnitudes decide what gets *designed*, measured ones decide what should. A scratch project against the pinned version costs minutes and does not touch the repo.
- 2026-07-25 [design] **Fixing one bug can *arm* another that was dormant only because the first one existed.** `RingGauge.active` could never be true (it required a single pid to fill an entire `max_block_frames` block in one tick, which the capture under-read and the mixer's over-production made impossible), so `DriftController::tick` skipped every output and the whole drift-correction path was dead code. It was dead code wrapped around an *inverted correction sign* — `ResampleRatio::new(1.0 + corr)` where `SincFixedIn` produces `consumed * ratio`, so a too-full ring would be corrected by filling it further. Repairing the flow control is exactly what makes the loop start running, against the wrong sign. When scoping work from an audit or a bug list, explicitly ask which findings are *masked* by other findings: an unreachable bug becomes reachable the moment its blocker is fixed, so it belongs in the same scope or the fix ships a regression the fix itself created. The audit's own suggested ordering had these five items apart.
- 2026-07-25 [design] **A pipeline's production quantum is set by whichever stage buffers in fixed chunks, not by the control policy that looks best in isolation.** Designing flow control for the mixer, deficit-to-target (produce exactly enough to bring each ring to a target fill, partial blocks included) is the textbook answer and holds fill tightest — and it was wrong here, because `audio_core::Src` wraps `rubato::SincFixedIn` whose `chunk_in` *is* `max_block_frames`: a partial push is buffered and produces no output at all until a full chunk accumulates, then emits a burst. The policy would have moved burstiness one layer down rather than removing it. Full-block-or-skip keeps every push chunk-aligned so the resampler emits on every tick it runs. Before choosing a variable-rate flow-control policy, look for a fixed-block stage downstream — it, not the policy, decides when output actually appears.
- 2026-07-25 [design] **Before designing a budget or rate limiter over a shared component, read how that component attributes work internally.** The mixer's governor was drafted with a single per-tick frame count bounded by the *fullest* output's ring — a design with a real cross-output starvation failure mode (one stalled output halting every other). Reading `mixer.rs` showed `push_group` sets that group's `valid_len`, `mix_tick` sums each group into its own output's accumulator, and `out.filled = out.filled.max(write_len)` — production per output is determined solely by the groups feeding it. So budgets are per-group, outputs never constrain each other, and the starvation mode cannot occur. "One call serves every consumer" (`mix_tick` runs once for the whole graph) does not imply "one budget serves every consumer."
- 2026-07-25 [implementation] **A per-rebuild-computed config value needs explicit plumbing into any longer-lived control loop that consumes it — the blueprint's contract text can name the compute-site without naming the wiring.** audio-flow-control's Level 4 said only "`build_running_graph` sets `DriftConfig::target_fill` from `drift_target_fill(..)`" — but `DriftConfig` construction actually lives in `supervisor_loop`, one thread that survives every rebuild, while `target_fill` depends on that specific build's own ring capacity/block size. Fix: `RunningGraph` gained a `drift_target_fill: f32` field, `SupervisorSnapshot` carries it out under the existing lock, and `supervisor_loop`'s per-topology-change branch now builds a fresh `DriftConfig` there instead of holding one `cfg` for the process's whole lifetime — only `target_fill` varies per rebuild, `kp`/`ki`/`max_correction`/`tick` stay the shared default. Check for this whenever a value computed at graph-build time needs to reach a thread whose lifetime spans multiple builds.
- 2026-07-25 [design] **A trait method that reports a real constraint must not get a default body — the counter-case to this codebase's own default-body rule.** The existing learning says to give a new port-trait method a default no-op when most implementors have nothing meaningful to do with it (`AudioSystem::set_bus_match`, `open_default_endpoint_volume`). That inverts the moment the method reports a *constraint* rather than offering a *capability*: a defaulted "free space available" answer is indistinguishable from an infinite device, which is precisely the condition the method exists to make observable. `RenderPort::free_frames()` therefore takes no default — every implementor, mock included, must answer honestly or the invariant it enforces is unenforceable. Ask which of the two shapes a new method is before reaching for the default-body precedent.
- 2026-07-26 [design] **Ask whether a hard problem is *inherent* to the architecture or *invented* by it.** A full day went into "how do we suppress a routed app's original audio stream?" — two real-hardware measurements, a survey of silent-sink placements, and a genuine undocumented-API-vs-setup-friction tradeoff. Studying the product being replaced showed the question only exists in a **tap** architecture: `PROCESS_LOOPBACK` copies a stream without consuming it, so two streams exist by construction and one must be hidden. A **transport** architecture (the app renders into your endpoint; you forward the only copy) never asks the question at all — SteelSeries Sonar has no double-audio problem, not because it solved one, but because it cannot have one. The reframing collapsed the whole solution space to "point the default at one silent sink" and deleted the per-app-redirect surface entirely, taking `IAudioPolicyConfigFactory` with it. Before optimizing a hard problem, check whether a different primitive removes it — and note the tell: this repo's own 2026-07-22 learning about auditing what the old primitive gave for free had already predicted this exact gap, so the warning existed and still wasn't reached for until the problem was studied from outside.
- 2026-07-26 [design] **Study the replacement target's *architecture*, not just its UI.** Splitstream copies SteelSeries Sonar's mixer UI closely — faders, groups, per-channel DSP — and the divergence was entirely in Windows integration: Sonar creates one Virtual Audio Device per channel and sets Game as default output / Chat as default *communications*, exploiting Windows' separate `eMultimedia`/`eCommunications` roles so Discord-class apps self-select with zero per-app config. That single fact explained the whole bug class. Strengthens the existing HeSuVi/Equalizer APO entry with the sharper form: **the place your product and the reference implementation differ is where the answer lives** — and it is worth going and looking there *before* spending measurement effort on the difference's symptoms. Note the follow-on discipline that mattered as much: the reference's model was studied and then *rejected* on its merits (endpoint-splitting is Sonar's separation mechanism; per-PID capture is strictly better and supports unlimited groups), so copying it would have been a regression. Study the reference to understand the problem, not to inherit the solution.
- 2026-07-26 [design] **A boolean that selects between two named platform enum values must be named and documented as a selector, not a flag.** `AudioSystem::open_process_capture(pid, include_tree: bool)` mapped `false` to WASAPI's `PROCESS_LOOPBACK_MODE_EXCLUDE_TARGET_PROCESS_TREE` — "capture everything on the system *except* this process" — while the trait doc read "`include_tree` captures the process's child processes too", which is purely additive phrasing. Every call site passed `false` from the feature's introduction, so each group captured every *other* app. It presented as a mixer bug (a paused app's fader showing a playing app's signal, one group's slider audibly affecting another, the shared output clipping because the same audio summed twice) and survived a full design, implementation and review cycle. When a parameter chooses between two named platform constants rather than toggling an optional extra, name it for the choice and spell out **both** branches in the doc comment.
- 2026-07-26 [design] **An abandoned investigation is not a constraint.** The 2026-07-21 pivot recorded per-app endpoint redirect as "proved unstable on real hardware" and moved the whole product off it — and that same decision log says, in its own words, *"root cause not fully isolated before the pivot decision — user explicitly chose to stop debugging."* Re-derived a session later: two of its three symptoms (bus `EndpointId` churn, topology mapping vanishing) belonged to the virtual cable that pivot deleted and cannot recur; the third ("per-app override silently failed to stick") is exactly what a wrong vtable produces, and this repo's own learnings record its `IPolicyConfig` sketch declaring 2 methods where the real interface needs 12 slots. Carried forward as fact, that claim would have foreclosed an entire solution family on unproven grounds. Extends the existing "reverse a decision by checking its stated reasoning's premise" rule to *unattributed* claims specifically: **check whether the reasoning was ever completed**, not only what it concluded — and mark such entries as unattributed when logging them, so a future reader knows the difference between a diagnosis and a stopping point.

- 2026-07-26 [design] **A design that deliberately places a new entity *outside* an existing subsystem's scope makes every event that subsystem emits blind to that entity.** double-audio-prevention's Level 2 recorded "observation plumbing is already complete... all three already reach the dispatcher — no new subscription," and that was true for device *additions* and default-device changes. It was false for removals: `handle_endpoint_lost` returns early when the removed endpoint is not an output any group uses, and the sink is **by design never a group output** — so the one entity the whole feature is about was precisely the case that produced no event at all. Flow F's stated trigger could not fire. The same design property that makes the sink safe (nothing renders to it) is what makes the existing recovery machinery ignore it. Sharpens the 2026-07-20 rule ("verify the underlying event stream can actually deliver the signal") with the trigger to watch for: when a design's *selling point* is that some new thing sits outside an existing subsystem's concern, re-read that subsystem's emit conditions for the scope test that will now exclude it. Found before writing the consuming code only because the flow was traced to a concrete early-`return`, not because the design doc was re-read.
- 2026-07-26 [design] **A rule of the form "never do X here" that is implemented as the *absence* of a call is invisible and one edit away from gone.** Flow E ("a default-device change made by the user or another audio tool is surfaced, never fought — two tools each re-asserting would ping-pong") had no representation in code beyond `handle_default_device_changed` not calling the assert path. Replaced with an `AssertTrigger::{Startup, ExternalDefaultChange}` value threaded into `sink_to_assert`, which has two real call sites and always answers `None` for the external one. The rule now lives at the exact line a future reader would be tempted to break, the test asserting it (`an_external_default_change_is_surfaced_and_never_re_asserted`) tests something real rather than a call that isn't there, and the cost is one two-variant enum. Applies to any deliberate no-op: prohibition encoded as omission cannot be reviewed, tested, or grepped.

- 2026-07-26 [design] **A lifecycle where one action writes a record and another clears it needs *every* path that performs the action to also write — and a design that names the pairing in only one branch will lose it.** double-audio-prevention's flow B paired "record the default being displaced" with "take the default" in step 2 (the user's one-time click). Step 3 — "thereafter every start re-asserts the sink" — said only *re-asserts*. Implemented faithfully, so: run 1 recorded, quit restored and cleared; **every run after that took the default recording nothing, and every clean quit left the machine parked on a silent sink.** Not an edge case, the normal path, and the worst state the feature can produce. Missed by 478 green tests *and* by a full review pass that had specifically audited the clearing logic — because the review asked "does this branch clear correctly?" and never asked **what establishes this branch's precondition on the second iteration**. Caught only by a user running it on hardware twice in a row. Two transferable checks: for any write/clear pair, enumerate every actor that performs the action and confirm each one writes; and when reviewing a restore/clear path, trace the *second* cycle, not the first. The fix that generalises is structural — return the action and its bookkeeping as a single value (`SinkTakeover { edits, sink }`) so "take without recording" stops being expressible, rather than adding the missing call at the site you happened to notice.

## Implementation Craft

- 2026-07-19 [implementation] When a blueprint's contract references a type documented under a sibling component that the build order constructs later, relocate the type to the earlier-built *consumer* rather than reordering the build or fully decoupling — same interface-at-consumer idiom as port traits, extended to config/DTO types. Recurred 2026-07-20 (P3's `MatchRule`/`GroupRules`, contract text put them under `control` but `engine::routing`'s own API needed them) — worth treating as a standing rule to check for, not a one-off.
- 2026-07-19 [implementation] For unfamiliar or fast-moving external crate APIs (major-version churn), verify exact signatures by writing the call and reading the real compiler error, not from memory or pre-written notes — notes can predate a dependency's breaking change; the compiler is ground truth. When a crate's own docs aren't browsable in-session, this is also faster than hunting for docs.
- 2026-07-19 [implementation] Before committing to a dependency's latest major version, check for accidental package-name collisions in its transitive tree (an external crate can happen to share your own workspace crate's name) — breaks `cargo build/test -p <name>`. Pinning to an older minor that matches already-written internal documentation can dodge both the collision and an API rewrite at once.
- 2026-07-19 [implementation] RAII guards for OS thread-affine resources (COM apartments, etc.) can't be struct fields on a type required to be `Send + Sync` — use a lazy per-thread `thread_local!` initializer called at the top of every method that touches the resource instead.
- 2026-07-19 [implementation] Real-time thread orchestration functions (open ports → compute timing → build the mixer → spawn N thread kinds → assemble a handle) accrete responsibilities fast and quietly cross the parameter-count/size thresholds — `#[allow(clippy::too_many_arguments)]` on a hot function is a signal to extract a context struct right then, not a thing to suppress and revisit later. Caught one review cycle later than it should have been.
- 2026-07-19 [implementation] A design's L3 interaction chain can name components a later, unbuilt phase owns (e.g. "gain → DspChain → duck → matrix → SRC" when DspChain/duck are P5 and not yet in the repo). Check the actual current code before implementing, not just the blueprint text — slot the new stage where the future component will insert, rather than stubbing a hook for it or blocking the whole feature on the other phase landing first.
- 2026-07-19 [implementation] Before threading a new field through a domain type (e.g. adding `layout` to `Format`), grep for every site that constructs that type raw from an external source — duplicated derivation logic (three places independently rebuilding `Format` from a raw `WAVEFORMATEX*`) is invisible in a blueprint that names only one of them, and adding new parsing logic to all three independently triples the chance of getting risky unsafe code wrong in exactly one spot. Consolidate to one shared function first, then add the field.
- 2026-07-19 [implementation] Existing `#[ignore]`d real-hardware tests are a normal implementation-time validation step for platform-boundary features, not optional polish saved for later — running one against real hardware mid-implementation caught in seconds what a mock structurally cannot (e.g. confirming a mask-decode path against the actual device that motivated the feature), turning a "should work" into a "confirmed on the real device."
- 2026-07-20 [implementation] windows-rs's `#[implement]` macro (COM callback interfaces, e.g. `IMMNotificationClient`) expands to absolute `::windows_core::...` paths — these only resolve if `windows-core` is a *direct* Cargo dependency at the version `windows` pins internally, not merely available transitively through `windows`. A transitive-only dependency fails with `E0433 could not find windows_core`, with no hint pointing at the fix.
- 2026-07-20 [implementation] A struct that owns windows-rs COM interface handles (e.g. `IMMDeviceEnumerator`, `IMMNotificationClient`) needs an explicit `unsafe impl Send` to live behind a `Mutex` on a `Send + Sync`-bound type — windows-rs interface wrappers are `!Send` by default. Sound exactly when every thread touching COM in the crate already joins one apartment (MTA) first via a shared `ensure_initialized`-style guard; reuse that existing safety argument rather than re-deriving it per type.
- 2026-07-20 [implementation] An in-repo "reference pattern" comment for undocumented/hand-declared COM (even one that explicitly warns "verify against the real source before use") can still be wrong on the exact thing it warns about — a sketch in this repo's own implementation-notes.md showed 2 real methods for `IPolicyConfig` where the actual interface (verified via a live fetch of EarTrumpet's source) needs 12 own vtable slots (8 unused + 2 more unused + 2 real). Treat any such sketch as a pointer to go verify, never as the verified answer itself, even when it says so.
- 2026-07-20 [implementation] Hand-declaring a WinRT/`IInspectable`-derived COM interface (`windows-core`'s `#[interface]` macro) when the crate version has no generated `{Parent}_Impl` trait for that base (true for `IInspectable` in windows-core 0.62): declare the trait as `: IUnknown` instead and manually placeholder-slot the base interface's own extra methods ahead of the real ones (`IInspectable` adds 3: `GetIids`/`GetRuntimeClassName`/`GetTrustLevel`) — produces an identical vtable layout, since ABI correctness depends on memory layout, not which Rust trait hierarchy describes it.
- 2026-07-20 [implementation] Before writing code against a fast-moving GUI/native-integration crate (tray-icon/muda, global-hotkey, tao, eframe), a few targeted WebFetch docs.rs lookups for the exact constructor signatures, thread-affinity requirements, and trait method names paid for themselves directly — four such crates in one session compiled clean or near-clean on the first attempt, versus the multi-round compile-fix churn every un-verified guess produced elsewhere. Worth the lookup specifically for native-integration crates, where API shape and platform requirements (not just names) are easy to get wrong from memory.
- 2026-07-22 [implementation] When the fast-moving GUI/native-integration crate needing API verification is already a workspace dependency, grep its real source directly from the local cargo registry cache (`~/.cargo/registry/src/*/crate-version/`) instead of a WebFetch to docs.rs — faster, works offline, and exact-version-matched by construction (no risk of reading a newer/older API than what's actually pinned in Cargo.lock). Used here to verify egui 0.35's `dnd_drag_source`/`dnd_drop_zone`/`Slider::vertical`/`ComboBox::from_id_salt`/`AsIdSalt` before writing any call (mixer-ui-redesign) — compiled clean on the first attempt across all three implementation layers. Reserve the WebFetch approach for crates not yet vendored locally.
- 2026-07-20 [implementation] A new block-based FFT convolution algorithm (uniformly-partitioned overlap-save / frequency-delay-line, spatial-audio's `PartitionedConvolver`) is fully verifiable through pure unit tests with hand-derived expected values — unit-impulse identity, a 2-tap moving-average closed form, and a multi-partition impulse reconstruction (impulse longer than one partition) — before any real audio device or even a full `Spatializer` is involved. Caught the exact one-partition output delay and multi-partition FDL-shift indexing correct on the first pass because the math was worked out by hand against the test, not just "sounds about right."
- 2026-07-20 [implementation] Wrapping a fixed-block-size algorithm (FFT convolution partition size B) behind a per-call arbitrary-length `process(input, output) -> same length` contract: prime the output ring with B silence samples at construction, then push/pop exactly one sample per input sample fed (running a block whenever the input accumulator fills). Gives a provably-bounded backlog (max B+1, proven by the invariant "produced count after n samples fed is `B*(1+floor(n/B))`, always >= n") with a trivial correctness argument — reusable for any block processor that needs a streaming per-sample-call API without letting callers deal in fixed block sizes.
- 2026-07-22 [implementation] A time-decaying block-fed meter/telemetry value (level-meters' `PeakMeter`, an env tail, any release-ballistics gauge) freezes at its last value the moment its source goes idle — a zero-length block carries zero frames, so the per-frame release recurrence never advances and the bar/value sticks. "Drive it with signal" tests never catch this; it only shows when the signal *stops* (a silenced group, a muted or idle output — `filled==0`/`valid_len==0`). Give the value an explicit silence-advance path (`observe_silence(frames)`, closed-form `env *= release.powi(frames)`) and call it with the tick's nominal frame count wherever the real block is empty, so time keeps passing for the meter even when audio isn't. Same shape as the per-frame-vs-per-element ballistics rule: the bug is a mismatch between "frames of audio processed" and "time actually elapsed." **Direct consequence, caught in review 2026-07-22:** once the value keeps advancing through silence, an exponential release *never reaches zero* — it decays into subnormal floats (~26 s after silence at a 300 ms release / 48 kHz) and stays there forever, so a flush-to-zero guard (`if env < 1e-9 { env = 0.0 }`) becomes mandatory in a way it never was for an envelope that freezes when idle (`EnvFollower` does nothing on a zero-frame block, so it can't reach that state). The cost lands on the RT thread, where FTZ isn't set, and shows up per-frame whenever a silent-but-still-pushing source delivers zero-filled buffers rather than empty ones. Add the guard in the same change as the silence-advance path. Pairs with a publish detail: a peak+clip (f32 + bool) reading crossing threads should pack into one `AtomicU64` (peak in the low 32 bits, clip in bit 32) so the pair can't tear — a stale clip flag against a fresh peak — and so a zeroed cell already decodes to the silent/no-clip resting value.

- 2026-07-20 [implementation] Flipping a binary to the Windows GUI subsystem (`#![windows_subsystem = "windows"]`) silently voids every `eprintln!`/`stderr` diagnostic and `exit(1)` message — there's no console to receive them, so a double-clicked app fails invisibly. The subsystem flip and an alternate diagnostic surface (file logger + panic hook → native dialog) must land in the *same* change, never as a follow-up; gate the flip behind `cfg(not(debug_assertions))` so dev builds keep the console. Same runtime-only-surfacing shape as the eframe/COM apartment gotcha — no unit test catches it.
- 2026-07-21 [implementation] A windows-rs type with a *real* (not hand-declared) `Drop` impl can still cause memory corruption when you manually construct one holding a pointer the `Drop` impl doesn't expect — `PROPVARIANT`'s `Drop` calls `PropVariantClear`, which for `VT_BLOB` calls `CoTaskMemFree` on `blob.pBlobData`; a blob pointer into a Rust-`Box`-owned struct (not `CoTaskMemAlloc`-allocated) gets freed through the wrong allocator the moment the value drops. Fix is `ManuallyDrop`-wrapping the *outer* value itself, not just an inner union field already wrapped for the same reason — confirmed by comparing against a real working implementation (`wasapi-rs`'s process-loopback activation) that double-wraps for exactly this. Caught by an actual `STATUS_HEAP_CORRUPTION` crash on the first real-hardware run, not by any static check. Generalizes: any manually-constructed windows-rs union/struct that owns a pointer needs its *whole* value's `Drop` behavior audited, not just the specific field being set.
- 2026-07-21 [implementation] A reference sample's offhand comment ("could also call X instead") is not verification that X works — Microsoft's own `ApplicationLoopback` sample notes `GetMixFormat` as an alternative to its hardcoded capture format, but calling it on a process-loopback-activated `IAudioClient` returns `E_NOTIMPL` on real hardware: that specific client type doesn't support format negotiation at all, unlike every other `IAudioClient` this codebase opens. Caught in seconds by running the `#[ignore]`d real-hardware smoke test against a live pid before shipping the assumption — treat any "or you could" aside in reference material as unverified until actually run, same as a hand-declared vtable sketch.

- 2026-07-21 [review] For config/script written in a build-tool DSL this environment can't compile-check (Inno Setup `.iss`, and by extension CI YAML, other installer/packaging DSLs — no toolchain installed to run it against), a live docs lookup before finalizing isn't optional polish the way it might be for a compiled language — it's the *only* verification available, since there's no compiler to eventually catch a wrong directive/value. Caught one real question this way (`ArchitecturesInstallIn64BitMode`'s valid values) that turned out already correct, but would have shipped as an unverified guess either way without the lookup. **Recurred immediately once the toolchain became available**: docs-lookup verification is a *substitute* for compiling, not equivalent to it — a real `iscc` compile the same session caught a flag (`runasoriginaluser` assumed valid in `[UninstallRun]` by symmetry with `[Run]`) that no doc skim had actually been run against for that specific section, and further investigation showed no such flag exists there at all (a genuine Windows/UAC platform limitation, not just wrong Inno syntax) — `runascurrentuser` is the closest available, with a real accepted-tradeoff edge case (standard user elevating with different admin credentials under-cleans HKCU on uninstall). When the real toolchain is available even once, compile against it before treating a docs-lookup-verified script as done.

- 2026-07-22 [implementation] An error enum whose `String` payload is read only via derived `Debug` at diagnostic call sites (`eprintln!("{e:?}")`, `tracing::warn!(?e, ...)`) trips clippy's `dead_code` lint as a false positive under `-D warnings` — the derive doesn't count as a "read" for dead-code analysis (clippy says as much in the lint note). Fix is `#[allow(dead_code)]` on the type with a one-line comment explaining why, not stripping the field down to `Variant(())` — that destroys the real diagnostic detail the field exists to carry. Recurring shape in this codebase: `app::lifecycle::ShellError` (caught here) and `engine::ports::PortError::Backend(String)` share the exact pattern.

- 2026-07-22 [review] When hand-deriving a custom-painted polygon icon (`egui::Shape::convex_polygon`, or any convex-only fill primitive), verify convexity by checking the sign of consecutive edge cross-products before writing the point list — a shape that's conceptually two convex parts joined at a seam (responsive-ui-refinement's speaker icon: a rectangular body + a horn/triangle sharing an edge) is very often concave overall right at that seam, even though each part alone looks convex when sketched by eye. The API's own doc note ("fill only supported for convex polygons") doesn't stop you from feeding it a bad point list — nothing catches it until the pixels are actually inspected or the math is checked; caught here by a cross-product sign-flip check during review, not by any test or compile step. Fix shape: split into separate `convex_polygon` calls per genuinely-convex part instead of one combined outline.

- 2026-07-26 [implementation] **When measuring "is data flowing", assert on *content*, not traffic volume — and never on a single read taken immediately after starting a stream.** Two failures in one diagnostic, both of which produced confident wrong answers. First, the `#[ignore]`d real-hardware capture test read once directly after `IAudioClient::Start()` and reported `0 samples` regardless of whether the source was playing — it raced WASAPI's first buffer period, so a false negative was indistinguishable from a real one. Fixed by polling to a 2s deadline. Second, and worse: once it *was* polling, the sample **count** was 188160 in the healthy case and 189120 in the fully-broken one — the stream keeps flowing at full cadence when a session is muted, every frame simply zeroed. A count-based assertion would have reported a clean pass on a completely silent capture. Only **peak amplitude** separated them (`0.0814` vs `0.0`). Any "is it working" probe over a streaming API needs a content measure; frame counts, packet counts and callback counts all stay healthy through the exact failures worth catching.

- 2026-07-26 [implementation] **Adding a port-trait method whose name a mock already uses for an inherent test hook compiles clean and silently redirects every call site to the hook.** `MockSystem` had `pub fn set_default_output(&self, id: EndpointId)` as a seed-the-fake helper; `AudioSystem` then gained `fn set_default_output(&self, id: &EndpointId) -> Result<(), PortError>`. Rust resolves inherent methods before trait methods, so `sys.set_default_output(x)` keeps hitting the fake — no error, no warning, and a test asserting the real method's behaviour would quietly exercise the hook instead. Different parameter types (`EndpointId` vs `&EndpointId`) don't disambiguate; they just change which call sites still compile. Grep the mocks for a candidate name *before* naming a new port method, and rename the hook (here: `seed_default_output`) rather than relying on call sites to disambiguate. Related, same change: the mock's new trait impl was made to *reject* an endpoint it doesn't have, because a mock that accepts any id cannot express "the sink isn't installed" — the exact condition the feature exists to observe (2026-07-25's rule about doubles that never say no).

- 2026-07-26 [implementation] **"Best-effort" describes what a helper does about failure, not whether its callers may ignore the outcome — the moment one caller records state around it, the return type has to change in the same edit.** `Dispatcher::set_default_output_by_name` returned `()` and logged, matching every sibling COM helper in this codebase (all genuinely fire-and-forget: assert the sink at startup, re-assert on a trigger). A comment stating the safe behaviour makes unsafe code read as deliberate and reasoned, which is strictly worse for a reviewer than no comment at all; the comment is where the intent lives, so it is also where a mismatch hides best. When auditing a swallow-and-log helper, list its callers and ask which of them *branch* on the outcome — and read the comment as a claim to verify, never as a description to trust.

- 2026-07-26 [implementation] **`cargo test` being green says nothing about the binary you actually launch — verify the exe contains the fix before believing a "didn't work" report from running the real app.** A fix was reported as not working; it had never executed. `cargo test` compiles a test harness, not `target/debug/<app>.exe`, so the launched binary was 17 minutes stale and still contained the *pre-fix* log string. Two cheap checks that settle it in seconds: compare the exe's mtime against the changed source, and `grep` the exe for a unique string introduced by the change (a new log message works well, and its *absence* is as informative as its presence). Related trap from the same session: a running instance blocks the rebuild with `Access is denied (os error 5)` — which `cargo build` reports without ever saying "something is holding the file", so a rebuild can appear to fail for no reason while the stale binary stays in place.

## Quality Signals

- 2026-07-25 [review] A test-quality anti-pattern can survive even when the author's own design doc explicitly warned against it. audio-flow-control's decision 4 rejected wall-clock test pacing by name ("the exact flakiness shape the operational learnings flag twice") — and the implementation still wrote a new test synchronizing two threads via two flat `sleep(20ms)` calls, in the very file that already has an established poll-until-deadline idiom for exactly this problem (`a_pid_whose_capture_thread_dies_mid_stream_is_reaped_and_retried`'s `while cond && Instant::now() < deadline { sleep(20) }`). One of the two sleeps turned out to be pure dead weight once inspected — the paced mock's release mechanism is a counter, not a one-shot signal, so calling it before the consumer thread even starts is already safe. Check new synchronization code against the *existing idioms already in the file being edited*, not just against the design doc's stated principles — a principle can be stated and violated in the same session, but a sibling function doing the same thing correctly is sitting right there to copy.
- 2026-07-22 [review] A widening **destructuring tuple** is the invisible sibling of parameter-count creep. Clippy's `too_many_arguments` polices function signatures, and this codebase responds to it well (`GroupColumnCtx`, `MasterColumnCtx`, `CaptureFaultCtx` all extracted at the threshold) — but *nothing* warns on a "pull everything out of the shared state under one lock" tuple, so level-meters grew one to 12 elements in the very file that had just been refactored for the same reason. Bonus signal for review: the tuple grew because three fields of one already-clonable struct (`stats.group_peak`/`output_peak`/`output_names`) were cloned individually instead of cloning the struct once — a widening tuple often points at a value that was decomposed too early.

- 2026-07-20 [review] When a log/telemetry line needs a derived scalar from a domain object that's already constructed for real elsewhere in the same code path (spatial-audio's `log_channel_conversions` called `HrirSet::embedded(rate)` a second time, off the same rate, purely to read `.taps()` — `Render::build`/`Mixer::new` had already built the real one for the actual `Spatializer`), expose a cheap pure accessor for the derived value instead of reconstructing the whole object. - 2026-07-19 [review] In a fallback/precedence table written as `match` arms, an unguarded arm always wins once its pattern matches — it silently bypasses a shared catch-all that sibling arms fall through to correctly. Inconsistent guarding across otherwise-parallel arms (3 of 11 speaker-fold rules unguarded, 8 correctly guarded) let one function's own documented "never lose audio" contract quietly break for a subset of valid inputs. When reviewing or writing this pattern, check every arm for the same guard-vs-unguarded shape, not just a sample of them.
- 2026-07-20 [review] When a param-threshold refactor (extract a context struct once a function's parameter list crosses the too-many-arguments line) gets applied to one of two structurally-mirrored functions, the sibling is easy to leave un-refactored — the reviewer catches it, not the author, because each function individually still "looks fine" in isolation. - 2026-07-20 [review] Multiple faults/events landing in the same poll-loop tick that each independently trigger a full rebuild/re-sync (rather than batching into one) is an easy-to-miss N-times-the-cost edge case — worth explicitly documenting as an accepted tradeoff at the point of implementation (same style as this codebase's already-documented concurrent-rebuild race), so a later reader doesn't mistake it for an oversight.
- 2026-07-20 [review] A test asserting "signal A is attenuated relative to reference B" on a value that's spread across several decaying taps (a spatial-audio HRIR's head-shadow kernel, an envelope tail, any short FIR spread) must compare peak/max magnitude, not sum-of-absolute-values — summing several taps each close to the per-tap attenuation can add up to more than one single-tap reference value even though every individual sample is correctly attenuated. - 2026-07-25 [review] **A green test suite alongside a reproducible production symptom is a signal to inspect the test doubles' capacity and timing assumptions first, before the production code.** `cargo test --workspace` was 118 pass / 0 fail while routed audio was audibly broken, because `SinkRender::wait_event` returned `Ok(())` immediately (no clock), `write` did an unconditional `extend_from_slice` (never rejects), `period_frames()` was a hardcoded `480`, and `SineCapture::read` returned `Ok(buf.len())` whatever the buffer's size. Four independent production bugs — over-popping a ring, over-producing per tick, under-reading capture, zero-padding partial blocks — were all *structurally unobservable* by that suite: no assertion could have caught them, because the doubles model an infinitely fast, infinite-capacity peer. - 2026-07-26 [review] **When a blueprint ships a Level-4 test-contract table, diff the implemented test names against it before writing `status: complete` — an untested *named* contract predicts bugs far better than any coverage number.** double-audio-prevention's L4 listed `clean_quit_restores_the_previous_default_and_clears_the_key`; it was never written. - 2026-07-21 [review] A picker/onboarding UI that lets a user independently pick two config fields referencing device/resource names (e.g. simple-launch's onboarding `bus_endpoint` picker + a "default output" fallback for `output_device`) must actively exclude the case where both resolve to the same underlying resource, whenever a downstream step assumes the two are disjoint (here: `engine::graph::resolve` requires `bus_endpoint` to classify `Bus` and `output_device` to classify `Physical` — same name for both can never satisfy both). - 2026-07-23 [review] A new pure helper function written *alongside* an interactive widget is easy to leave untested even though it needs no UI framework to test — it doesn't read as "the widget" (so it dodges "this needs a live frame" reasoning), and it also isn't an axis/mapping function with an obvious test-contract slot, so it falls into neither bucket a design doc's test table tends to enumerate. graphical-eq's `hit_test_handle` (nearest-handle-within-radius, used by every drag/click/scroll/remove) was exactly this: pure, load-bearing, zero test contract in the design doc, zero coverage until review caught it. Sixth occurrence this session-block of a new type/function's single most load-bearing piece shipping untested. When reviewing a widget's interaction logic, explicitly check every helper function it delegates a decision to, not just the ones that already look testable (axis mapping, formatters) — a hit-test/matcher/filter helper is exactly as testable and exactly as easy to skip.

- 2026-07-24 [design] Wake *frequency* is not the CPU-cost driver on a real-time thread — the wait *primitive* is. `mixer_loop` already woke at almost exactly the same cadence as `render_loop`'s genuinely-event-driven `WaitForSingleObject` (its `tick_period` was defined as half the render period, i.e. roughly the same order of magnitude), yet cost measurably more CPU, because it used `spin_sleep` (sleeps most of the interval, then busy-spins the tail for precision) instead of a true blocking wait. A user's competitive benchmark (VoiceMeeter/Sonar/Broadcast all <0.1% idle CPU, all WASAPI-based) exposed this — the fix wasn't "wake less often," it was "block instead of spin" (`thread::park_timeout` triggered by real producer events, replacing the independent timer). When a thread's cost doesn't match its apparent wake rate, check what it *does* between wakes before assuming the rate itself needs to drop.
- 2026-07-24 [design] A timing constant serving double duty — both a sleep/wake interval and a buffer-sizing basis — is a coupling that breaks silently if one purpose changes without re-deriving the other. `tick_period` (half the render period) was simultaneously `mixer_loop`'s sleep duration *and* the input to `compute_max_block_frames`'s scratch-buffer sizing; redesigning the wake mechanism without noticing the sizing dependency would have changed how much audio gets processed per wake, a real underrun risk, not just a timing tweak. Caught by tracing `compute_max_block_frames`'s actual call graph before touching `mixer_loop`, not assumed. When a constant's doc comment or name suggests one purpose, grep every call site before changing what produces it — it may be quietly load-bearing somewhere unrelated to its apparent job.
- 2026-07-24 [implementation] Testing "did a real-time tick run / drain everything" against actual audio content is unreliable when the pipeline includes a real resampler: `audio_core::Src` always runs a genuine `rubato::SincFixedIn`, even at a 1:1 nominal ratio (kept variable for continuous drift correction), and that resampler has real warm-up latency — a first tick's `take_output` legitimately returns zero samples regardless of whether the tick itself ran correctly. mixer-demand-driven-wakeup's first draft of `mixer_loop_ticks_immediately_on_first_run_before_any_wake`/`..._drains_everything_pending_...` asserted on mixed output samples and failed even though the redesign was correct — fixed by asserting on `RingGauge.active` instead (set purely from `pull_group_inputs`' own full-block-fill bookkeeping, unaffected by anything downstream of `push_group`). When a test's job is "did this internal mechanism run/coalesce correctly," assert on that mechanism's own bookkeeping, not on output several pipeline stages downstream that may have independent, legitimate latency of its own.
- 2026-07-24 [implementation] `std::thread::park`/`unpark`'s documented token-persistence (an `unpark()` before the matching `park()` still makes that `park()` return immediately) makes wake-call regression tests both race-free and boundable: spawn the "mixer" side calling `park_timeout(generous_bound)` and recording elapsed time, run the real function under test, then assert `elapsed` is small. A bare `park()` with no timeout would hang the test suite forever if the wake call ever regresses (production bug becomes a CI hang, not a red assertion); `park_timeout` + an elapsed-time assertion turns "did it wake me" into a fast, deterministic pass/fail either way. Used for mixer-demand-driven-wakeup's `render_loop_wakes_the_mixer_after_draining_its_ring`/`pid_capture_loop_wakes_the_mixer_after_producing_a_block`.
- 2026-07-24 [review] When redesigning a thread's wakeup mechanism from a fixed clock to an event-driven wake, audit every place the OLD mechanism was implicitly relied on for prompt reaction — not just the steady-state tick path. mixer-demand-driven-wakeup's own Flows A-I covered startup/idle/audio/capture/command/coalescing/multi-output/telemetry, but missed the shutdown/rebuild exit path: `stop_running_graph` set the `stop` flag but never called the new `wake()`, silently regressing shutdown/rebuild join latency from ~5-10ms (old fixed clock) to up to the fallback bound — a path that had ridden the old mechanism's side effect for free and was never itself one of the design's named flows. Caught only in an independent review pass, not the same session's own cross-component check. Whenever a wake/pacing mechanism changes, specifically grep every `stop.store(true` / thread-join site the changed thread participates in, not just the flows the design document enumerates.

- 2026-07-24 [design] **A save/restore batch built from a "target state" must diff against *live* state field-by-field, not unconditionally emit one edit per field.** profiles.md's L3 pseudocode read as "build the full edit list, then classify the batch," but that would always include `SetGroupOutput` (even when the output device hadn't changed), which the codebase's `edit_path` classifier marks `Structural` — forcing a full engine rebuild on *every* profile switch, including a pure gain change, directly contradicting the decision that motivated the classifier in the first place ("a gain-only profile must never rebuild"). The fix (`control::profiles::apply_profile` comparing each target field against the corresponding live field and emitting an edit only on a real difference) is also what makes a capture-then-apply round trip a genuine no-op rather than a batch of redundant same-value writes — the two properties come from the same diff, not two separate mechanisms. Generalizes to any "restore a named snapshot" feature building a mixed-classification edit batch: diff against current state before classifying, never classify an unconditionally-built batch.
- 2026-07-24 [implementation] **A "modified since saved" indicator is cheapest and least likely to drift when computed by re-deriving the pure snapshot function and comparing via the type's own `PartialEq`**, rather than hand-writing a field-by-field comparator that must be kept in sync with the value object's actual fields by hand. `control::profiles::profile_is_modified` calls `capture_profile` (the same pure builder `Save` uses) and compares the result against the stored value directly — adding a field to `ProfileGroupConfig` later can't silently desync the modified check the way a parallel hand-written comparator could. Same shape as the "prefer the authoritative source over a lookalike reconstruction" family of learnings, applied to a boolean derived value instead of a UI label.
- 2026-07-24 [review] **A doc comment claiming "each item is handled independently, one bad one never blocks the rest" must be checked against every fallible step in the batch, not just the one the author had in mind.** `spawn_hotkeys`'s doc comment made that exact claim, and it was true for *registration* failure (`run_hotkeys` filters with `manager.register(*hotkey).is_ok()`) but false for *conversion* failure — `to_global_hotkey(chord)?` in the collection loop used `?`, so the first bad chord aborted the whole function, dropping every other binding including `mute_master`. Currently unreachable (the two functions gating which chords are constructible vs. convertible happen to agree today), which is exactly why no test caught it — the gap is latent until they drift. When a function processes N independent items and claims per-item isolation, grep for every `?`/early-return in the collection loop, not just the step the isolation was designed around.
- 2026-07-24 [implementation] **Generalizing a single hotkey/tray-menu-item registration to N bindings**: build a `HashMap` from the platform's own opaque id (`HotKey::id()`, `MenuId`) to a small action enum at *registration* time, inside the thread that owns the event loop, rather than threading a growing parameter list or a chain of `if id == x { } else if id == y`. `hotkeys.rs`'s `spawn_hotkeys`/`tray.rs`'s `build_menu` both went from "exactly one id compared with `==`" to "map lookup over an id → action table" — the dispatch loop's body didn't need to grow per binding kind, only the map's construction did. Reusable whenever a fixed set of platform-registered ids needs to fan out to more than one caller-defined action.

- 2026-07-24 [review] **A hook added to a function that already runs on every snapshot change inherits that function's call frequency — check what the hook actually costs before assuming "runs often" is fine.** `Dispatcher::set_current` already ran on every param edit, including every frame of a fader drag (egui's `Slider::changed()` fires per-frame, not just on release, and no debounce exists upstream). Adding `tray_handle.rebuild()` there (external-controls' capability 9, "the tray must never show a stale group list") inherited that same per-frame call rate, but a native tray-menu rebuild (destroy+recreate `Menu`/`Submenu`/`CheckMenuItem`) is real OS-level work, unlike the plain-data operations `set_current` already did there. Fixed by comparing a cheap `PartialEq` snapshot of just the tray-relevant fields before and after, skipping the rebuild when nothing changed. Generalizes: before adding a hook to an existing frequently-called function, check the hook's own cost against the function's actual call rate, not just whether the *existing* work at that call site was cheap.
- 2026-07-24 [design] **Third occurrence of "diff against current state before emitting, don't unconditionally build the whole edit shape."** profiles.md's `apply_profile` needed this (unconditional emission would classify a gain-only switch as `Structural`); external-controls' `reconcile` returning `AdoptFromEndpoint{level, muted}` as one unconditional pair (never just one field) meant the caller had to re-diff both fields against current state anyway before emitting edits, or a plain volume-key press would also emit a same-value mute edit that a downstream push-outward hook mistook for a real mute change. When a pure decision function bundles multiple fields into one "apply this" result, treat that bundling as a hint the *caller* still needs its own before/after comparison per field — the bundle's presence doesn't mean every field inside it actually changed.

- 2026-07-24 [implementation] A design contract's own pseudocode can name a library method that doesn't exist in the pinned version, the same way a design doc's stated *mechanism* can be wrong even when the fix is right (see the db-faders `SliderClamping` entry above) — visual-identity.md's Level 4 wrote `install(...)` as `set_visuals_of` x2 + `set_style` + `set_theme`, but egui 0.35 has no `set_style`; the real per-theme mutation surface is `set_visuals_of` (replaces `Style.visuals` wholesale, per theme) plus `all_styles_mut` (applies one mutation to both `dark_style`/`light_style`). Applying the intended shared style meant copying only `style()`'s specific fields (spacing, corner radius, stroke width) onto each already-colour-installed `Style` via `all_styles_mut`, never replacing `.visuals` wholesale a second time — that would have discarded the accent colours `set_visuals_of` had just installed. Caught by grepping the local registry source before writing `install`, not by trusting the contract's literal call sequence. Generalizes the existing "verify unfamiliar crate APIs against the compiler, not memory" rule one step further back: a blueprint's own pseudocode is exactly as unverified as memory until checked against the real pinned source.
- 2026-07-24 [design] A design's prose can name several distinct-sounding refresh triggers for the same piece of derived state (visual-identity.md decision 9/Flow G: "at startup", "on every tray-menu rebuild", "opportunistically while the settings window is open" for the tray icon's system-theme-following) without that meaning three separate call sites are needed. All three collapsed into one mechanism — `Dispatcher::refresh_tray_icon`, called from the dispatcher's *already-existing* 50ms poll tick (the same loop `check_push_to_mute_expiry` already runs on), comparing `(accent, resolved system theme)` against a cached last-pushed value and only doing real work (re-render + cross-thread send) on an actual change. Before wiring separate call sites for each named trigger in a design's prose, check whether an existing cheap poll/tick already covers all of them via one state comparison — the "opportunistic" and "on rebuild" triggers turned out to be the same fact (an existing tick loop noticing a change) described from two different angles, and "at startup" was just that same check's first-ever run.

- 2026-07-24 [review] Copy-pasting an established code shape can silently cross the "extract it" threshold even when each individual copy looks like the obvious, minimal-diff choice. `store.rs`'s `SetTheme`/`SetAccent` write arms each repeated the exact `doc["app"].or_insert(...).as_table_mut().ok_or_else(malformed_app_shape)?` block `SetAutostart`/`SetActiveProfile` already used — 2 prior copies were borderline (arguably fine inline), but the 2 new ones pushed the total to 4, past the "3+ occurrences" extraction line. Before copy-pasting a pattern that already appears in a file, grep how many times it already exists — the new code's own copy count isn't the only one that matters.
- 2026-07-24 [review] A design's Level-4 test-contract name can describe an invariant already enforced by a function's *signature* (no accent parameter reaches `semantic(theme)` at all — decision 5, visual-identity.md), and the naive implementation of that contract compares two identical calls to the same pure function, which is trivially true regardless of whether the code is actually correct. When a test's name matches something the type system already proves at compile time, the runtime assertion needs to check something the signature doesn't already guarantee (here: that dark/light actually produce distinct values, not both silently defaulting to the same fallback) — otherwise the test provides zero regression protection while still reading as if it does. **Recurred 2026-07-26** (double-audio-prevention review): `a_start_finding_previous_default_already_set_leaves_it_intact` asserted that an `&AppConfig` input was unchanged after the call — something the borrow checker already proves, so the assertion could never fail. Fix shape both times is the same: assert the *output* exhaustively (here, pin the whole returned edit list) rather than re-stating an invariant the signature carries.

- 2026-07-25 [design] A design doc's Level-2 component table can split components that must actually compile together, because the table groups by *responsibility* while the compiler groups by *crate*. routing-truthfulness.md listed `match_session`/`MatchKind` (component 1), `AppConfig.excluded` (component 2), and the routing read model's `RoutedSession` (component 3) as three separate rows — but all three live in the `engine` crate, and `engine::routing` calls `match_session` directly, so widening its signature meant all three had to land in one buildable checkpoint, not a three-step sequence. Before planning code-forge's inside-out implementation order from a blueprint's component table, map each component to its actual crate first — components in the same crate that call each other directly are one build-boundary layer regardless of how many rows the table gives them.
- 2026-07-25 [implementation] When only some items in a shared list type need extra per-item metadata that others don't have (routing-truthfulness.md capability 4: `MatchKind` provenance only makes sense for a *matched* session, not one sitting in the unassigned pool because nothing matched it), thread the metadata as a separate pid-keyed lookup map (`ChipZoneCtx.kinds: &HashMap<u32, MatchKind>`, empty for the unassigned zone) alongside the existing plain list, rather than widening the list's element type everywhere. The alternative — putting `RoutedSession` into the shared chip-list type — would have forced the unassigned zone to fabricate a `MatchKind` for sessions that were never matched at all, a lie in the data even when never rendered.

- 2026-07-25 [review] A feature's own capability wording can promise more than a related-but-out-of-scope matching tier actually delivers, and the gap survives because it's pre-existing rather than newly broken. routing-truthfulness.md's capability 3 says an unreadable-path session "never produces a routing rule" — true for the drag path (new `is_draggable` gate + `ExactName("")` guard), but a bare `*` catch-all glob still matches an empty file name (`wildcard_match` untouched, `"*".matches("")` == `true`), so a pre-existing catch-all group still silently captures such a session exactly as it did before the fix. Not a regression — B10's grounding explicitly scoped the fix to the drag gesture and the exact-name tier — but reviewing only the diff's own tests would never surface it, since nothing there changed. When a capability's stated guarantee spans multiple matching tiers (exact/pattern/catch-all here), check the wording against every tier the underlying mechanism touches, not just the one the blueprint chose to fix, even when — especially when — the other tiers are "out of scope."

- 2026-07-26 [review] **A symptom that reproduces identically across unrelated inputs indicts the shared layer, not per-input state.** A paused Plex window's fader showed live signal, and raising a *different* group's slider made it worse. The obvious reading was "Plex isn't really silent when paused" — plausible, and it sent the investigation into the mixer's meter plumbing, `GroupId` ordering and buffer aliasing, all of which came back clean. The decisive datum was the user swapping a YouTube tab in for Plex and getting the **identical** result: two unrelated applications cannot share an app-specific quirk, so the defect had to live in the layer common to both, which was capture. That single substitution collapsed the search space after hours in the wrong subsystem. When a symptom is app-specific by hypothesis, the cheapest next test is to change the app — and treat a byte-for-byte identical result as an indictment of the shared path, not a coincidence.
